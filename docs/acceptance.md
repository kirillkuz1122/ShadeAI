## Ограниченный сбор метрик

`scripts/acceptance_probe.py` — Python≥3.11 stdlib, без установки новых библиотек.
Только GET `/api/v1/health` по явному числовому RFC1918/loopback/ULA IP (также IPv4
link-local), без DNS/proxy/Bearer/redirect/retry. HTTPS использует проверку системным
CA и IP SAN; отключать проверку сертификата нельзя. Нет чтения.env, команд HA, БД,
аудио, argv/env процессов. Health сам проверяет HA только чтением.

Пишутся фиксированные числовые поля/enum: health, host MemAvailable/Swap/uptime,
хеш текущего boot-id, UTC/monotonic. Неизвестные строки заменяются unknown; raw
ответы/URL/ключи/названия устройств и процессные команды в JSONL не записываются.
`--pid` читает только процесс своего UID и его потомков≤128/≤256threads на процесс,
останавливается при пропаже/повторном использовании корневого PID. RSS sum может
дважды учитывать общие страницы, пропустить короткий пик и **не включает HA/ОС**.
Для всего cgroup Core явно задать его каталог v2: memory.current/peak/swap.current/
oom_kill. Отсутствующий файл→null, это не нулевой расход или отсутствие OOM.
[Семантика cgroup](https://docs.kernel.org/admin-guide/cgroup-v2.html),
[proc](https://docs.kernel.org/filesystems/proc.html).

Запускать на **той же машине, что Core**, от service-user; иначе host/PID-метрики
относятся к машине оператора. Платформа определяется по реальному device-tree+
aarch64; компьютер помечается development_host. Даже на Pi результат всегда
`hardware_acceptance=false`: утилита не подписывает акт приёмки. LLM ready означает
только загрузку движка, качество/инференс проверяются отдельно.

По умолчанию всего1замер. Ниже **ручной будущий запуск на Pi**, не выполненные14дней:

```bash
sudo install -d -o shadeai -g shadeai -m 700 /var/lib/shadeai/acceptance
sudo systemctl show shadeai.service -p MainPID -p ControlGroup
sudo -u shadeai /usr/bin/python3 /opt/shadeai/scripts/acceptance_probe.py --url http://127.0.0.1:8000/api/v1/health --output /var/lib/shadeai/acceptance/run-01.jsonl --samples 20161 --interval 60 --pid <MainPID> --cgroup /sys/fs/cgroup<ControlGroup>
```

Заменить placeholders реальными значениями. Для отделения от SSH-сессии использовать
свою службу/screen/tmux на Pi; автоматическая установка наблюдателя здесь не выполнялась.
Если Core под другим UID/в контейнере, выбрать корректный namespace/PID/cgroup либо
явно оставить эти метрики отсутствующими. Не брать общий cgroup пользовательской
сессии с Claude/другими службами за расход Core. Сборщик отдельно от Core, не его child.

Новый файл600/каталог700, существующие файлы/symlink не перезаписываются; append/
автовосстановления после перезапуска нет. До начала запас≥4GiB+32MiB, во время≥4GiB;
при RAM<64MiB прекращает сбор, чужая запись может расходовать резерв. Лимит32MiB/
20161замер/запись≤1536байт, HTTP≤8с/response≤72KiB; данные не накапливаются в памяти.
Максимальный интервал3600с, пример60с;20161точка охватывает14дней только при реальном
непрерывном времени между первой/последней, без сбоев/вмешательств. Короткий стенд с
ускоренными часами этого не доказывает. При нештатном kill/дисковой ошибке JSONL
может не иметь summary — такой прогон неполон; новый запуск всегда в новый файл.

Summary содержит только число замеров/ok/degraded/errors/замеченных разрывов/время/
причину остановки. Проверять health_degraded/errors/discontinuities и cgroupOOM,
не только завершение sample_budget. Sampling не обнаруживает все короткие отказы;
сопоставить журнал systemd, uptime, наблюдения пользователя и модельные измерения.
Не суммировать несколько перезапущенных файлов в «14дней без рестартов».
