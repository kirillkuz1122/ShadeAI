# TASK-15 — очередь обработки уведомлений

**Дата:** 2026-10-18. **База:** fffc175. **Статус:** выполнена. LLM и распознавание текста не подключены; аппаратные задачи остаются открыты.

## Реализация

- `NotificationWorker`: один consumer, FIFO, ограниченная Queue только ID (64 по умолчанию, 1..256) и одна активная запись. Остальной backlog хранится в SQLite и подчиняется retention. POST после commit только будит worker через Event, резервный опрос 1 с исключает зависимость от доставки сигнала. create_task-шина не используется.
- Ревизия **0006_notification_processing**/ORM добавляет processing_status/attempts/error_code/started_at/finished_at и индекс. Существующие строки pending/0, прежние is_processed/JSON не выдаются как результат нового конвейера. Прежние данные/ID сохраняются. Downgrade сохраняет AUTOINCREMENT и исторический sqlite_sequence, включая уже удалённый наибольший ID.
- Перед обработкой atomic UPDATE/commit фиксирует processing/attempt; транзакция не удерживается во время handler. Переходы pending→processing→processed/failed. Приватность, формат, срок и допуск проверяются до handler; финальный UPDATE по id/digest/attempt/status/TTL/допуску не восстанавливает удалённую строку.
- По умолчанию **disabled**, обработка не имитируется. Явный **diagnostic** сохраняет строго `{"processor":"diagnostic","llm":false}`, без категории/извлечения сущностей/отражения текста. Старый фиксированный ответ noise удалён. Обработчик — чистый async/cancellable контракт, без команд HA; CPU-инференс требует отдельного исполнения в TASK-16.
- Таймаут/исключение/невалидный результат дают безопасный terminal failed; следующие записи продолжаются, failed автоматически не повторяется. Результат проверяется строгой схемой, неизвестные поля запрещены. Сырой результат/исключения/SQL-параметры не логируются. При сбое фиксации повторяется только commit одного проверенного результата, без повторного вычисления. Неопределённый исход claim восстанавливается в том же процессе после восстановления БД.
- Shutdown ждёт активную попытку до 5 с, затем отменяет; queued ID остаются pending в SQLite. Processing после рестарта становится pending/PROCESSING_INTERRUPTED с прежним attempts. Готовые/failed не переигрываются. Stop идемпотентен и выполняется до engine.dispose. После аварии вычисление может повториться: гарантия не exactly-once, поэтому побочные действия в handler запрещены.
- Сохранён Android-совместимый POST receipt stored/duplicate/skipped. GET расширен processing_* и фильтром processing_status; старый status=stored/processed остаётся совместимым. Health показывает состояние worker, llm_status остаётся not_loaded. [Контракт](../api-spec.md#414-состояния-обработки--task-15).
- Web показывает ожидание/обработку/ошибку/диагностический результат, число попыток и безопасную причину. Diagnostic явно отделён от AI-анализа. Карточка обновляется каждые 5 с через useResource/AbortSignal, скрытая вкладка не опрашивается. Неизвестные коды не отражаются raw; старый Core без новых полей поддерживается.

## Воспроизведение

Из `core/`:

```bash
.venv/bin/python -m pytest -q
.venv/bin/ruff check app tests migrations checks
.venv/bin/python checks/check_notification_worker.py
```

Из корня проекта:

```bash
docker build -t shade-core:task15 core
docker run --rm --network none \
  -v "$PWD/core/checks/check_notification_worker.py:/app/checks/check_notification_worker.py:ro" \
  shade-core:task15 python checks/check_notification_worker.py
```

Стенд создаёт временный каталог core/.pytest_cache/task15-loopback-*, запускает дочерний --serve только с синтетическим процессором отказов, закрывает все процессы/HA и удаляет каталог. Runtime diagnostic не содержит режимов искусственного зависания/ошибок. Браузер — по [инструкции Web](../../web/README.md#статусы-обработки-core-task-15), сценарий [processing.js](../../web/checks/processing.js).

## Ограничения и следующий шаг

Модель, русский NLU, категории/интенты, автоматические действия и Pi не проверялись. Async-handler обязан не блокировать event loop и уважать отмену; текущий diagnostic CPU-инференс не выполняет. Вынос реальной модели из event loop и поведение занятого движка при timeout относятся к TASK-16. Один процесс Core на БД; RAM-лимит ID не является квотой диска. Retention может удалить долго ожидающую запись. HTTP retry для failed пока отсутствует. После аварии чистое вычисление может повториться, side effects запрещены. Изменение конфигурации требует перезапуска; default disabled оставляет pending до явного включения диагностического/будущего реального обработчика.

**Следующая TASK-16:** локальный движок/модель и измерения; без Pi доступна программная подготовка на компьютере, аппаратные критерии 4 GB/RAM/охлаждения/качества остаются до TASK-08. Пользователь не может предоставить железо сейчас, повторно не запрашивать.

Сохранение исторического счётчика при batch-rebuild сверено с [официальным описанием SQLite AUTOINCREMENT/sqlite_sequence](https://www.sqlite.org/autoinc.html) и отдельно проверено на upgrade/downgrade.
