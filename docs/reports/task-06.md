## Что было и что изменилось

До задачи существовали REST-методы HA и POST ha/action; клиент создавался для запроса, автоматической записи EventLog не было. Health не проверял доступность БД, локальная ротация логов отсутствовала.

Теперь реализованы:

- GET /devices с фильтром domain, GET /devices/{entity_id}/state, POST /devices/{entity_id}/command. Все требуют Bearer Core. Чтение живое из HA, без локального кэша.
- Общий AsyncClient на lifespan с закрытием при shutdown, пулом 8/2, проверкой сертификата HTTPS, без redirect и proxy-переменных окружения. HA_TOKEN отделён от ключа Core. Пустой HA_TOKEN означает HA_NOT_CONFIGURED без сетевого запроса.
- Общий бюджет одного HTTP-обмена HA_TIMEOUT_SECONDS=5 (0.1..30), включая чтение тела; ping также ограничен 2 секундами. Ответ до 2 MiB декодированных данных и 5000 состояний; JSON и схема состояний проверяются. Команда и последующее чтение имеют отдельные бюджеты.
- Проверка entity_id, домена/сервиса и JSON параметров; тело команды до 64 KiB. Нельзя заменить цель через params/data. Нет автоматической повторной отправки.
- Безопасные коды ошибок соединения, авторизации, таймаута, ответа HA и аудита. Исходные ответы, параметры, токены и тексты исключений в ошибки не включаются.
- Совместимый POST ha/action с прежними domain/service/entity_id/data, включая data=null. Старые поля ответа status/entity_id/result сохранены, добавлены метаданные; маршрут deprecated, удаление пока не планируется без перехода клиентов.

Успешный POST означает принятие сервиса HA и сохранённый аудит. Ответ вызова HA содержит состояния, изменившиеся за время вызова, и не доказывает состояние цели. Поэтому Core отдельно читает целевую сущность. При отказе чтения возвращается success с new_state=null/state_observed=false; физическое выполнение и достижение нужного состояния не объявляются подтверждёнными.

## Аудит и хранение

Одна строка events_log на попытку:

1. До сети фиксируется command_requested/pending. При отказе начальной фиксации возвращается AUDIT_UNAVAILABLE/not_sent, в HA ничего не отправляется.
2. Транзакция завершена до ожидания HA, блокировка записи SQLite не удерживается.
3. Строка получает command_executed/success либо command_failed/failed. outcome различает accepted/rejected/not_sent/unknown; failed/unknown не гарантирует отсутствие действия в HA.
4. При отказе итоговой фиксации клиент получает AUDIT_FINALIZATION_FAILED, event_id и известный outcome. Сохранённый pending остаётся для диагностики. Следующий старт меняет pending на command_interrupted/unknown с CORE_RESTARTED, не повторяет команду.

В payload только request_id/entity_id/domain/service/status/error_code/outcome. Params, атрибуты, ответы HA и токены не сохраняются. GET /events требует Bearer и отдаёт только команды HA с проекцией безопасных полей, total, limit/offset, фильтрами времени и типа; ID в обратном порядке. Дата to включает весь день UTC, timestamp to исключителен. Неизвестный type и неверный диапазон — 422.

EVENT_RETENTION_DAYS=90 (1..365), очистка при старте и ежечасно, просроченное сразу скрыто из API. Ревизия 0004_event_journal сохраняет поля/ID прежних строк и добавляет индексы времени, источника/типа и AUTOINCREMENT. Старые ревизии не менялись. Перед обновлением/изменением хранения требуется копия; логическое удаление не стирает старые копии и остатки SQLite/WAL.

## Health и служебные логи

Health открыт, проверяет БД через SELECT 1 и ping HA. Доступная БД с отказом/отсутствием HA даёт HTTP 200/degraded; отказ БД — HTTP 503/error. Доступность HA не блокирует приём уведомлений. Старые поля сохранены; добавлены db_connected, db_size_bytes, ha_status и services. Размер включает SQLite+WAL без SHM; при ошибке определения — null/unknown. LLM, notification_worker и analytics показывают not_loaded/not_implemented. Это не полный integrity check БД и не проверка физических устройств.

Стандартный logging пишет в LOG_DIR/shade.log: старт/остановка, event_id/статус/код команды и безопасные сообщения обслуживания. Ротация по UTF-8 байтам: по умолчанию 1 MiB + 3 архива, файлы 600 при каждом открытии/ротации; новый каталог 700. Проверка обнаружила и устранила потерю закрытых прав после ротации. Логи исключены из git/Docker-контекста; пример Docker сохраняет их в /data/logs. Console/access logs Uvicorn и их эксплуатация на Pi остаются TASK-08.

Web API-клиент получил типы/методы устройств и журнала, новые поля health, ApiError со status/detail, чтобы TASK-07 могла показать код/outcome/event_id ошибки. Android health DTO принимает дополнительные поля с defaults. Интерфейсы клиентов в этой задаче не расширялись.
