## Что сделано

Два явно выбранных binary_sensor: личное присутствие TASK-20 и независимое общее присутствие **всех жильцов**. Нужны свежие live-переходы одного направления, согласованные времена/окно/дни, connected/checkpoint и отсутствие gaps. Другой человек дома блокирует выключение света общим состоянием on. Неверные часы, unknown/snapshot/разрыв/один источник не превращаются в действие. Реальная независимость/покрытие общего датчика ещё не доказаны — это условие конфигурации и аппаратной проверки.

Только ранее подтверждённые конкретные light.* и turn_on/turn_off. Новая version1-политика/approval_scope включает источники, режим, задержку и cooldown. После перехода с21/смены политики нужно новое решение; при включённом режиме без совпадающего scope сервер отказывает409, старый клиент не активирует новые условия молча. Web/Android показывают второй источник/задержку/cooldown, не принимают неизвестную политику. Никаких HA-действий из LLM.

Миграция0009 и bounded durable журнал. Pending с задержкой отмены30с (10..120), затем повторная проверка; ручная отмена/disable/reject подавляют ожидающее действие. Состояние dispatching фиксируется до аудита/сети, дальше отмена не обещает отката. Cooldown цели1800с (300..86400), один переход не переигрывается. После рестарта pending отменён, dispatching unknown, автоповтора команды нет. execute_command остаётся общей точкой аудита, сеть вне DB-транзакций. Сбой финализации не вызывает новый HTTP.

Protected GET automations/runs, POST cancel; Web показывает последние20 действий/причины/отмену/unknown. История до1000 записей, TTL90дней, при заполнении прунятся только terminal старше суток; свежие ID не теряются, при нехватке места новых кандидатов нет. Детали — [контракт](../api-spec.md#446-исполнение-приходаухода--программная-task-22), [Core README](../../core/README.md).
