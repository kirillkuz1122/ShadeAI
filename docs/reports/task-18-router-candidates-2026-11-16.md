# TASK-18: отдельная модель для классификации уведомлений

Идея Кирилла от 16 ноября 2026 года. Сначала исследование по карточкам моделей,
ниже dev-проверка без новых весов и без изменения рабочего обработчика.

Проблема наблюдается в новом [замере](task-18-holdout-2026-11-16.json): 0/4
правильных категорий транспорта и 8/30 отказов проверок ответа. Классификатор
может помочь с такси, доставкой и рекламой. Он сам по себе не извлечёт адрес и
не исправит неподтверждённую цитату. В [TASK-19](task-19-native-staged-2026-11-16.json)
обе захваченные Android-записи Qwen отклонила; успешный контроль шёл через API.

| Кандидат | Что показывают первичные источники | Решение для опыта |
| --- | --- | --- |
| [Jev TypeSafe](https://docs.typesafe.ai/introduction) | Типизированный выбор, оценки и вероятности; документированный продукт использует API TypeSafe | Облачный API не подходит Zero-Cloud. Берём идею, не провайдера |
| [Laya](https://huggingface.co/convaiinnovations/laya) | Основной вариант настроен на английский | Для русских уведомлений не первый кандидат |
| [Laya Multilingual](https://huggingface.co/convaiinnovations/laya-multilingual), [экспорт ONNX](https://huggingface.co/verdict-models/laya-multilingual) | Локальный многоязычный классификатор; есть сторонний экспорт в ONNX. [CPU ONNX Runtime](https://onnxruntime.ai/docs/get-started/with-python.html) доступен для Linux ARM64 | Первый кандидат для сравнения; проверить конкретный граф, токенизатор, русский и суммарную память Pi, не подставлять GGUF в существующий Qwen runner вслепую |
| [CMF Decision](https://huggingface.co/infosave/cmf-decision) | Компактный отдельный формат, рантайм Cortiq и обученные сценарии; карточка помечена English | Запасной кандидат после доказательств русского качества и прогона на Pi ARM64 |
| [Clef-Flash](https://huggingface.co/Cloudflare/clef-flash) | Основан на Qwen3.5-9B | Не пробовать на Pi 4 GB: вариант 6,2 ГБ со скриншота уже слишком большой для нашего бюджета |

Место опыта — в worker после допуска/записи, перед извлечением. Выход маршрутизатора
ограничен пятью существующими категориями и вариантом «не уверен». Сначала его
прогноз только сравнивать с разметкой, не менять обработку/отправку. Сохранение
оригинала, строгая проверка цитат, нормализация даты в коде и запрет действий по
LLM-результату остаются. Низкая уверенность не должна выбрасывать уведомление.

Порядок: сравнить простой локальный вариант без новых весов с Qwen на dev; затем
отдельно проверить Laya Multilingual с теми же условиями и на новой необученной
русской выборке. Измерять полное совпадение полей, путаницу taxi/delivery/noise,
пропуски важных событий, долю вызовов Qwen, холодную/прогретую задержку и пиковую
память **Core + HA + процессы моделей** на Pi 4 GB. Карточки и размер весов
не подтверждают эти показатели. Включать новую зависимость только при выигранном
сравнении и сохранении Zero-Cloud; до проверки не держать два движка резидентно.


## Первый эксперимент без второй модели

В [правилах](../../core/checks/compare_notification_router.py) учитываются только
слова в заголовке и тексте, без пакета приложения и поля разметки. Одна категория
по найденным признакам → метка, конфликт или отсутствие признаков → воздержание.
[Сопоставление v1](task-18-router-rules-v1.json) и [сопоставление v2](task-18-router-rules-v2.json)
связывают прежнюю Qwen с теми же примерами по хешу набора, ID и ожидаемой категории.

| Просмотренный набор | Только Qwen | Правила: верно / отвечено | Воздержались | Правило или сохранённая Qwen |
| --- | ---: | ---: | ---: | ---: |
| v1, 40 строк | 29/40 | 32/33 | 7 | 38/40 |
| v2, 30 строк | 16/30 | 28/28 | 2 | 28/30 |

Транспорт: правила 5/5 и 4/4 против 1/5 и 0/4 у Qwen. В v1 одна неверная метка
правила; 38/40 и 28/30 — подстановка категории в таблице, без нового вывода модели.
Это не точность полных полей, не число сэкономленных вызовов и не основание пропускать шум.
Оба набора просмотрены. Хеши 30 входов v2 добавлены в dev-реестр, чтобы их нельзя было
повторно пройти с `--stage holdout`; исходный ноябрьский отчёт сохранён неизменным.

Чтобы проверить полные поля, отдельный `--router-rules` у QA-измерителя
фиксирует предсказанную категорию в JSON Schema Qwen. При воздержании используется
обычная схема. Во всех случаях модель действительно запускается, затем штатный
парсер проверяет цитаты и временные поля. Ни сохранение, ни продакшен Core не меняются.


## Нативная проверка ограничения категории

[Полный отчёт](task-18-router-native-dev.json), [guard](task-18-router-native-guard.json).
Одна и та же Qwen по SHA-256, хеш промпта, базовая схема, набор v2, версия Python и
llama-cpp-python, контекст 2048 и два потока. Адаптированная схема у 28 строк, 2 воздержания.
Выход модели не исправлялся заменой категории после парсера; все 30 вызовов без сети.

| Метрика v2 | Qwen | Правила ограничивают категорию Qwen |
| --- | ---: | ---: |
| Правильная категория | 16/30 | 21/30 |
| Валидный ответ | 22/30 | 21/30 |
| Полное совпадение размеченных полей | 11/30 | 16/30 |
| Доставка + напоминания, все поля | 10/20 | 12/20 |
| Доставка, все поля | 3/10 | 3/10 |
| Напоминания, все поля | 7/10 | 9/10 |
| p50 / p95 / max, с | 2.995 / 4.139 / 5.085 | 3.651 / 5.004 / 6.678 |

Пять доставок отклонены, в том числе одна без метки правила. Улучшения полного
результата — две строки напоминаний, две транспорта, одна шума; ранее точные
строки остались точными. 9/30 ответов отклонены вместо 8/30. Пик RSS процесса
модели 2067992576 байт против 2063798272, не общая память Core+HA и не Pi. Замер
выполнен на общем компьютере в разных проходах; задержки наблюдаемые, причины
разницы не изолированы. Защита не прерывала 133.596 с прогона; exit 1 по порогам.

Оставить как dev-эксперимент. Смена схемы класса не закрывает задачу и не позволяет
сократить число вызовов. Следом локально проверить, какие поля приводят к отказам,
и оценить извлечение только подтверждённых фрагментов текста до траты диска/RAM
на второй движок. Рабочий Core не использует правила или новый рантайм.

Воспроизведение из `core/` (имена выходных файлов должны быть новыми):

```bash
.venv/bin/python -m checks.compare_notification_router \
  --dataset checks/eval-notifications-2026-11-16.json \
  --reference ../docs/reports/task-18-holdout-2026-11-16.json \
  --output .pytest_cache/router-rules-v2.json
.venv/bin/python checks/run_native_guarded.py --seconds 360 \
  --output .pytest_cache/router-native-guard.json -- \
  .venv/bin/python checks/evaluate_extraction.py --router-rules --stage development \
  --dataset checks/eval-notifications-2026-11-16.json \
  --model models/qwen2.5-1.5b-instruct-q4_k_m.gguf \
  --output .pytest_cache/router-native-dev.json
```

Проверки: 35 целевых тестов, полный Core **547**, ruff и production-сборка Web прошли.


## Почему Qwen отказывает после маршрутизации

[Повтор девяти отказов](task-18-router-diagnostics.json), [guard](task-18-router-diagnostics-guard.json).
Сверены хеш набора, модель, версия правил и решения по строкам. Повторяли только
подмножество, отдельным процессом, без обычного полного порядка вызовов. Это
диагностика, не новый замер точности. Все 9 отказов повторились при конечном
`finish_reason=stop`, поля прошли JSON и Pydantic, но не проверку буквального источника.

| Поле без буквального подтверждения | Строки |
| --- | ---: |
| Время | 5 |
| Тема | 2 |
| Сервис | 2, из них 1 отличие регистра |
| Место | 1 |

В одной строке два проблемных поля, поэтому число полей больше числа ответов.
Выход содержит только ID, служебные коды и классы ошибок; сырых ответов нет.
Отказы не исправлялись и строгая проверка не ослаблялась. Следующий кандидат —
давать модели выбор из ограниченного списка буквальных фрагментов (сначала для
времени), сохраняя `null`/неуточнённость при конфликте, прежде чем пробовать ещё
один движок. Проверять не только valid-rate, но и точность времени на новых данных.

Повтор из `core/`, в существующем offline guard после остановки других тяжёлых стендов:

```bash
.venv/bin/python checks/run_native_guarded.py --seconds 150 \
  --output .pytest_cache/router-diagnostics-guard.json -- \
  .venv/bin/python checks/diagnose_extraction.py \
  --dataset checks/eval-notifications-2026-11-16.json \
  --evaluation ../docs/reports/task-18-router-native-dev.json \
  --model models/qwen2.5-1.5b-instruct-q4_k_m.gguf \
  --output .pytest_cache/router-diagnostics.json
```

После диагностики полный Core: **553 теста прошли**, ruff без ошибок. Web build прошёл на предыдущем срезе этого эксперимента; диагностический CLI Web не меняет.


## Эксперимент: время из исходного текста

Режим `--time-literals` работает только в измерителе на заранее зарегистрированном
dev. [Поиск кандидатов](../../core/checks/literal_time.py) читает title/text, не
разметку. Буквальные интервалы, день с часами, относительное время, дата и
несколько неуточнённых форм (например «скоро») идут в перечисление JSON Schema
вместе с `null`. Если кандидатов больше 12, цитата больше 128 символов или содержит
управляющие символы, ограничение не применяется. Для `noise` остаётся только `null`.
Распознавание ограничено описанными шаблонами; неизвестная форма времени может
остаться без кандидата. Строгий штатный парсер и нормализатор времени не менялись.


| Схема на просмотренном v2 | Валидно | Категория | Все поля / 30 | Доставка и напоминания / 20 | p50 / p95 / max, с |
| --- | ---: | ---: | ---: | ---: | ---: |
| Базовая Qwen | 22 | 16 | 11 | 10 | 2.995 / 4.139 / 5.085 |
| Только правила категории | 21 | 21 | 16 | 12 | 3.651 / 5.004 / 6.678 |
| Только буквальное время | 25 | 19 | 14 | 12 | 3.738 / 5.459 / 6.319 |
| Правила и буквальное время | 25 | 25 | 19 | 14 | 3.685 / 5.468 / 6.480 |

[Отчёт только время](task-18-literal-time-only-dev.json) / [guard](task-18-literal-time-only-guard.json),
[отчёт правила + время](task-18-literal-time-dev.json) / [guard](task-18-literal-time-guard.json).
Во всех проходах совпали модель, базовая схема, хеш промпта/набора и параметры
движка. Добавление кандидатов к правилам: 4 отказа больше не повторились в полном
проходе; 3 строки стали полностью точными, прежние точные строки не потеряны.
При этом 5 отказов остались, в том числе 3 доставки. Время по нормализации
resolution верно в 25/30 вместо 20/30 у одних правил; число кандидатов не превышало
лимит на этом наборе. Peak RSS процесса в связке 2070822912 байт. Новых загрузок нет,
защита не остановила ни один проход. Задержки на общем компьютере наблюдаемые,
измерения Pi/полный бюджет Core + HA не выполнены.

Выбирать связку для следующих стендовых проверок, не включать в рабочий Core:
14/20 и max6.480 с не отвечают целям. Следующий отдельный срез — повтор двух
синтетических Android-уведомлений TASK-19. Для независимой оценки понадобится
новая разметка, широкий охват форм времени и сравнение без изменения кандидата
по результатам. Диагностический CLI проверяет хеш режима и число кандидатов
перед воспроизведением этого отчёта.

Повтор из `core/`: взять прежнюю offline-команду из раздела выше и добавить
`--time-literals`, для проверки только времени убрать `--router-rules`. Каждому
проходу дать свои новые имена выходных файлов.

Проверки: 21 целевой тест, 564 Core, ruff, Web build; после согласования диагностики отдельные 17 целевых и проверка вхождения нового отчёта прошли.

## Эксперимент: буквальное название сервиса

`--service-literals` в dev CLI сужает `service` до явно упомянутых Ozon,
Wildberries или Яндекс Go с регистром исходника, либо `null`. Он не выводит имя
из пакета приложения, не принимает общие слова вроде «доставка», не меняет
ветку `noise` и не исправляет вывод после проверки. До 8 разных цитат, сверх
предела остаётся исходная схема. Этот узкий словарь может не покрыть другие
службы, поэтому не считается рабочей политикой. Диагностика проверяет хеш правил
сервиса и число кандидатов при повторе.

- [Два Android-текста](task-18-service-publisher-dev.json), [guard](task-18-service-publisher-guard.json):
  с сервисом 2/2 валидных и 1/2 полных против 1/2 и 0/2 у времени с маршрутом.
  `aosp-order` теперь принят; `aosp-big` по-прежнему ошибается в приоритете.
- [Знакомый v2](task-18-service-v2-dev.json), [guard](task-18-service-v2-guard.json):
  валидные 27/30 вместо 25/30, категория 26/30 вместо 25/30, полные 20/30 вместо 19/30.
  У транспорта 4/4 правильные категории; `ht03` стал полностью верным, потерь по
  прежним точным строкам нет. Доставка/напоминания по-прежнему 14/20, max5.823 с.
  `hn02` перестал падать, но остался неверно классифицирован. Та же модель,
  набор, промпт, маршрут, ограничение времени и параметры. Guard не останавливал.

Вариант остаётся в QA: требования качества и Pi не приняты. Для повтора добавить
`--service-literals` к командам dev выше. Следующий шаг TASK-19 — проверить этот
вариант на системном захвате в одноразовом AVD, если guard подтверждает запас.

Проверки словаря: 23 целевых, **570 Core**, ruff прошли. Web ранее собран на срезе времени; Web-код не менялся.
