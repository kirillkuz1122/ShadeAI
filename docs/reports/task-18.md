# TASK-18 — методика оценки LLM

**Статус:** инструмент и первый независимый синтетический замер выполнены. **Цели не достигнуты, TASK-18 открыта.** Промпт/выборка до первого замера зафиксированы после dev TASK-17; после просмотра ошибок v1 считается dev для дальнейших исправлений. Pi отсутствует.

## Набор и разметка

[eval-notifications.json](../../core/checks/eval-notifications.json), версия 1: **40 полностью синтетических** уведомлений, 10 delivery, 5 transport, 10 calendar, 10 reminder, 5 noise. Нет личных сообщений/банковских кодов/рабочих данных. Зафиксированы timestamp 2026-10-10T10:00:00Z и Asia/Yekaterinburg. Размечены category, priority, resolution/UTC at/local date. Для service/location/subject приведены допустимые буквальные значения; неоднозначные subject некоторых доставок/встреч не размечены. Эти поля не засчитываются автоматически правильными, их покрытие видно в знаменателях метрик. Напоминания имеют размеченный subject, noise — все пустые сущности.

Есть относительные/абсолютные даты, date_only, неподдержанные диапазоны/дни недели/голые часы, отмена/перенос, реклама с упоминанием такси/курьера, обновление календаря, инструкции внутри payload. Неподдержанное время по текущему контракту должно быть unresolved, **это не реализованное распознавание любой даты**. Невалидный JSON/timeout/cancel проверяются детерминированными тестами TASK-17, чтобы они не зависели от случайного ответа модели.

Разметка создана агентом и требует человеческого просмотра; набор мал и не описывает реальное распределение уведомлений. Он отдельный от 8 классификационных smoke TASK-16 и 4 отладочных примеров TASK-17, его ответы не включены в prompt/few-shot. При первом запуске фиксируются SHA-256 набора и промпта. Если после просмотра ошибок промпт изменён, повтор на той же версии является **повторным dev-замером**, не новым независимым подтверждением; для подтверждения подготовить новую выборку.

## Как считать

- Строгий production-parser/processor, те же schema/проверки цитат/нормализация, одна локальная модель. Warmup отдельно на dev-примере. Один проход по фиксированному порядку, без выбора удачных повторов/исключения failed. При ошибке результат null, все размеченные поля false; такие записи остаются в знаменателе.
- Classification accuracy, precision/recall/F1 пяти классов и macro-F1; valid structured output отдельно от правильности.
- Поля считаются отдельно с собственными знаменателями. Для строк — casefold/сжатие пробелов, без смыслового «похожести»; at/date/resolution точное совпадение. Модель могла цитировать подстроку корректно, но положить не в то поле — это ошибка метрики, не успех по факту JSON.
- Exact match требует всех размеченных полей, включая category/priority/time. Цель ≥90% применяется к **20 delivery+reminder**, справочно вычисляется Wilson 95% по [формуле NIST](https://www.itl.nist.gov/div898/handbook/prc/section2/prc241.htm). Даже 20/20 даёт нижнюю границу около 83.9%. Наши синтетические примеры не являются независимой случайной выборкой; интервал здесь лишь показывает ограниченность малого объёма, **не даёт статистического доказательства 90% на реальных уведомлениях**.
- Полная задержка вызова processor (prompt+RPC+native inference+валидация), p50/p95/max, включая ошибки; токены/ru_maxrss дочернего процесса. Это **не** задержка Android→WorkManager→HTTP→очередь→SQLite и не общий RSS HA+Core+ОС. Для строгого локального сравнения с 4 с используется max, не только медиана. Pi/сеть/очередь могут увеличить задержку.
- Выходной JSON содержит версии Python/llama-cpp-python, CPU/kernel, модель/хеш/контекст/потоки/память, хеш набора/промпта, все результаты по ID/ошибки, сводку. Сырые невалидные ответы не сохраняются.

## Запуск

Из core/, с подготовленной локальной GGUF:

```bash
.venv/bin/python checks/evaluate_extraction.py \
  --model models/qwen2.5-1.5b-instruct-q4_k_m.gguf \
  --output ../docs/reports/task-18-evaluation.json
```

Настройки/ключ одноразовые, рабочий `.env` не читается. Код выхода 1 означает недостижение эмпирических целей ≥90% delivery/reminder или max≤4 с; отчёт всё равно сохраняется. Успешный код выхода на компьютере не подтверждает аппаратную приёмку Pi. Для нового независимого набора — --dataset. Сначала закрепить TASK-17 на dev-примерах, потом запускать эту оценку.

**Проверки инструмента:** 4 unit-теста метрик/набора прошли: failed в знаменателе, ошибочная классификация/precision/recall, p95/max, покрытие полей/нормализация, Wilson/баланс/уникальные ID. Полный набор Core — 265 passed на Python 3.14.8 и Python 3.11.16 в Docker --network none; ruff/Web успешны. Реальный прогон проведён отдельно в offline namespace.

## Продолжение без подмены приёмки

1. Диагностировать восемь отказов по уже увиденному v1 через diagnose_extraction.py; сохранять только тип поля/ошибки, без raw-ответов. Исходный task-18-evaluation.json **не перезаписывать** — это первый независимый результат.
2. Исправлять общие причины на dev: качество буквальных цитат, различение такси/доставки/рекламы, контракт priority и полноту времени. Не хардкодить ответы по ID, не убирать поля из метрики и не заменять модель универсальной выдачей category.
3. После фиксации изменений подготовить **новый** синтетический набор с другими формулировками, зафиксировать хеши и повторить независимый замер. Повтор на v1 помечать dev. Разметку и качество на реальном распределении должен проверить человек, когда будут разрешённые данные.
4. Сократить стоимость промпта/инференса и измерить max, включая холодный случай и реальный конвейер; нельзя подменять максимум медианой. Профиль threads4/ctx2048 до выяснения native-выхода не использовать как принятый.
5. На Pi проверить общий RAM/HA/температуру/без сети. Отсутствие Pi не мешает исправлять программную часть, но не снимает критерий.
