# TASK-04 — Миграции и базовая схема данных

**Дата:** 2026-10-17. **Статус:** выполнена. **База:** `3b34be7`, ветка main.

## Что изменено

- Добавлены alembic.ini, окружение, шаблон новых ревизий и две миграции. Адрес БД читается из настроек Core, отдельный URL/секрет в ini отсутствует.
- `0001_legacy_schema` создаёт notifications_raw/events_log в пустой БД либо проверяет прежний скелет без изменения его таблиц и данных. Частичная/изменённая схема не принимается автоматически, stamp head не требуется.
- `0002_device_states` добавляет entity_id (TEXT, PK), state, attributes_json (TEXT, default `{}`), last_changed/last_updated (DATETIME UTC). Настоящая синхронизация HA ещё не реализована.
- init_db применяет upgrade head через AsyncConnection.run_sync в транзакции до приёма HTTP-запросов. Проверены повторный запуск и откат DDL/версии при ошибке. Использован [рецепт Alembic для asyncio и общей Connection](https://alembic.sqlalchemy.org/en/latest/cookbook.html#using-asyncio-with-alembic).
- Общая фабрика подключения сохраняет WAL, synchronous=NORMAL и foreign_keys=ON. Для транзакционного DDL отключён неявный BEGIN драйвера и установлен обработчик begin SQLAlchemy согласно [документации SQLite dialect](https://docs.sqlalchemy.org/en/21/dialects/sqlite.html#using-sqlalchemy-to-emit-begin-in-lieu-of-sqlite-s-transaction-control-all-python-versions-sqlite3-and-aiosqlite).
- API-fixtures используют ту же фабрику подключения и настоящие миграции. Изоляция окружения, БД и сети сохраняется.
- Docker-образ включает конфигурацию и миграции. README содержит команды Alembic, переход со скелета и пример согласованной копии через SQLite Backup API. Локальный каталог core/backups исключён из git и Docker-контекста.

Зависимости не добавлялись: Alembic уже был установлен. Эндпоинты и формат API не менялись; Android, веб-код и визитка не изменялись. Рабочие `.env` и БД не открывались; проверки использовали синтетические данные в игнорируемом core/.pytest_cache/.

## Проверки

### Pytest и линтер

Из core/:

```bash
.venv/bin/ruff check app tests migrations
.venv/bin/python -m pytest -q
```

**Результат:** ruff успешен, **43 passed, 1 warning** на Python 3.14.8. Предупреждение Starlette/httpx прежнее. В исходной базе было 29 тестов; добавлены 14 проверок миграций:

- Пустая БД достигает head, схема совпадает с ORM; server default JSON, обязательность дат и уникальность entity_id проверены.
- Независимый SQL-снимок прежней БД содержит два синтетических уведомления с разными ID, NULL/JSON и запись журнала. Миграция сохраняет все поля и прежние CREATE TABLE; два повторных запуска ничего не теряют. Новое уведомление после перехода получает ID больше прежних и ORM-defaults.
- Восемь вариантов несовместимой схемы отклоняются: неполный набор таблиц, тип, NULL, отсутствующий столбец, первичный ключ, лишняя таблица, view и индекс. Схема/строки сохраняются; alembic_version после ошибки не остаётся.
- Искусственный сбой после создания device_states откатывает новую таблицу и номер версии, сохраняет старые записи. Повторная миграция после устранения сбоя успешна.
- SQLite откатывает тестовый DDL и отклоняет нарушающую foreign key запись.
- Уже версионированная базовая БД обновляется; downgrade до базовой ревизии сохраняет уведомление; повторный upgrade успешен.
- CLI upgrade/current/check работает из другого каталога с явным конфигом и URL-кодированным нестандартным путём БД; проверено создание именно указанного файла.

### Docker / Python 3.11

Образ `shade-core:task04` успешно собран. В одноразовых контейнерах с `--network none` и отдельными файловыми БД выполнены два сценария:

1. Пустая БД: два входа в lifespan, health=ok, история уведомлений пуста, версия head, WAL и foreign_keys включены.
2. Прежний образ `shade-core:task01` создал настоящую БД скелета с уведомлением ID=41 и журналом ID=19. Новый образ дважды прошёл lifespan; health=ok, авторизованный GET notifications видит прежнее уведомление. Все поля обеих записей до/после совпали.

В контейнере Python **3.11.16**. HTTP-сценарии выполнены через ASGITransport с настоящим lifespan, без запуска внешнего HA или облачных сервисов. Контейнеры и тестовые БД удалены после проверки.
