# TASK-14 — сбор телеметрии Home Assistant

**Дата:** 2026-10-18. **Исходная ревизия:** df615f0. **Статус:** программная часть выполнена и проверена. Общий чекбокс открыт: реальные датчики HA не настроены, домашнее накопление на Pi не начато. TASK-08/27 остаются аппаратной/длительной приёмкой.

## Что изменено

- `core/app/services/telemetry/collector.py`: один фоновый сборщик на lifespan, auth → subscribe_events(state_changed) → get_states → события/ping. Повторное подключение с backoff 1→60 с и jitter до 20%, сброс после 60 с устойчивой сессии. При потере прикладного pong/неверном протоколе/ошибке БД — разрыв и новый baseline. Отказ авторизации/прав приостанавливает сеть до перезапуска.
- Явный выбор до 100 числовых sensor/binary_sensor, пустой список отключает сеть. Нечисловые sensor пока не поддерживаются; unknown/unavailable сохранены как отдельные состояния. В память текущего снимка/БД попадают только state и три разрешённых строковых атрибута; friendly_name/context/old_state/raw не сохраняются. Неизбранные события отбрасываются до записи.
- `store.py`, ORM и новая ревизия `0005_sensor_history`: выбранный DeviceState, sensor_history, telemetry_gaps и telemetry_checkpoint. Источник `ha_snapshot` отделён от `ha_state_changed`. Снимок/кэш/checkpoint/закрытие gap атомарны; после ошибки live-записи память не продвигается. Удалённая/не видимая сущность получает null в истории и удаляется из кэша.
- Границы разрыва берутся от последнего durable baseline/pong, консервативно включая интервал с последней успешной проверки (обычно 30 секунд плюс таймаут; при задержках больше). Аварийный рестарт восстанавливает gap по checkpoint. Синхронизация входит в gap: переходы до baseline не реконструируются. Точный повтор внутри сессии пропускается, регресс HA last_updated требует пересинхронизации.
- TTL 90 дней (1..365), глобальное окно последних ID до 100000 строк (1000..500000), максимум 1000 gaps и 100 состояний. Очистка на старте/записи/pong, при выключенном сборе/auth-паузе раз в минуту. Снятый выбор очищается с перезапуском. Лимит логический: не гарантирует уменьшение файла SQLite/физическое стирание копий.
- `GET /telemetry`, `/telemetry/history`, `/telemetry/gaps` — защищённое чтение локальных данных. Кэш помечен stale при разрыве/синхронизации, также консервативно при смене поколения baseline во время чтения. REST `/devices` и команды TASK-06 не меняют поведения; автоповторов команд нет. Контракт обновлён в [api-spec.md](../api-spec.md#426-телеметрия-ha--task-14).
- Прямой pin `websockets==17.1`. WSS проверяет сертификат; proxy/redirect/compression/wire-логи выключены. 2 MiB/5000 состояний, порог 16 кадров, 256 промежуточных сообщений при синхронизации, ограниченные таймауты. Ошибки/логи только с безопасными кодами.
- Core закрывает фоновые задачи до engine.dispose. Тестовый fixture больше не освобождает engine во время работающего lifespan.

## Ограничения и продолжение

Реальный HA, его версия/права/датчики, Pi/RAM/CPU/SD и длительное накопление не проверены. Даже при успешной программной проверке сбор домашней истории **не запущен**. Пользователь сейчас не может предоставить оборудование, повторный запрос не нужен. После TASK-08 явно выбрать нужные датчики и сверить события/разрыв/состояния с настоящим HA; для аналитики учитывать gaps, unknown/unavailable, обрезку истории и синхронизацию часов HA/Core.

Сборщик рассчитан на один процесс Core на БД. Настройка через окружение/.env и рестарт, без UI выбора. HA отправляет доступные состояния/события до локальной фильтрации; это не серверный фильтр подписки. Очень большой снимок HA сверх лимитов даёт явный отказ, не частичный baseline. Текстовые/time-сенсоры требуют отдельной политики. История — ограниченный буфер, резервные копии/физическое удаление — отдельный эксплуатационный регламент.

Следующая доступная **TASK-15** — ограниченная очередь обработки уведомлений, durable-статусы и восстановление с тестовым обработчиком; LLM пока не подключать.
