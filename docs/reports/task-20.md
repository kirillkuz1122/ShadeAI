# TASK-20 — профиль времени присутствия

**Статус:** программный срез реализован и проверен на синтетике. **TASK-20 открыта:** реальные 7–10 дней, подбор порогов на реальном распорядке и Pi не проверены. LLM/новые зависимости/команды HA не используются.

## Что реализовано

- Явный ANALYTICS_PRESENCE_ENTITY, default выключен; только binary_sensor из уже выбранного HA_TELEMETRY_ENTITIES. Пользователь выбирает сигнал присутствия on=дома/off=вне дома; датчик движения не становится присутствием автоматически. IANA ANALYTICS_TIMEZONE, период пересчёта 60–86400 с, default 1 ч.
- Чтение sensor_history, gaps и checkpoint. Снимок — baseline, не приход/уход. Текущий неполный день исключён. Каждый полный локальный день проверяется на покрытие, gaps, unknown/unavailable, скачки snapshot, неправильные/рассогласованные часы, чрезмерные переходы и дребезг. После пропуска переходы не восстанавливаются. Если старые gaps уже удалены лимитом хранения, более ранний интервал считается неизвестным.
- Последние 30 полных суток, отдельно будни/выходные; первый уход/последний приход за день. Поиск плотного кругового окна ±45 минут, включая полночь; календарные сутки учитывают DST 23/25 ч. Поддержка ≥80%, медианный разброс ≤15 мин, минимум 5 будних/4 выходных и общий охват ≥7 дней/покрытие ≥70%.
- Score = поддержка/допущенные дни группы × min(дни/10,1) × (1−медианный разброс/45) × общее покрытие. Это **эвристическая регулярность**, не вероятность и не статистическая гарантия. Пять идеальных будней дают 0.5. Нерегулярная/слишком короткая/плохо покрытая история не выдаёт уверенный профиль. Будущая автоматизация требует отдельного решения пользователя.
- Предел 10000 наблюдений (включая предыдущий baseline) и 1000 gaps; переполнение не скрывается усечённой выборкой. CPU в asyncio.to_thread, без открытой DB-транзакции на время расчёта. До 4 профилей, устойчивые ID для entity/timezone/kind/day_group.
- Новая миграция 0007_habit_profiles: habit_profiles и analytics_state. Результат/снимок атомарны, при сбое прежние данные сохраняются с stale. Пересчёт фоновый, корректная остановка до dispose БД; выключение очищает только производные профили/снимок. Настройки не расширяют сбор телеметрии.
- Защищённый GET /habits: профили, причины исключений, число наблюдений, статус/давность расчёта и telemetry_stale. Старый config_key не выдаётся. Нет action/target и разрешения управлять домом. Health services.analytics отражает настоящий статус вместо not_implemented. [Контракт](../api-spec.md#43-аналитика--программная-task-20).

Python 3.11 — существующий образ, --pull=never/--network none, read-only исходники, tmpfs 64 MB, память контейнера 768 MB; новый образ/зависимости не скачивались.
- Регулярные/нерегулярные истории, недостаток дней, низкая уверенность на одной неделе, разделение выходных, полночь/выброс, DST, gaps/открытый gap, unknown/неверные часы, snapshot, повторы, дребезг, stale checkpoint/будущее время и переполнение. Проверено отсутствие вызовов HA services.
- Миграция из старой БД/metadata и новый round-trip 0006→0007→0006→head: исходные уведомления/журнал не меняются, производные таблицы корректно создаются/удаляются.
- **Настоящий Uvicorn/HTTP/перезапуск:** [JSON](task-20-loopback.json). Синтетические 28 суток, после каждого из двух запусков 4 профиля с одинаковыми ID, 28 допущенных дней, auth/health PASS, журнал команд пуст. От старта до готового ответа около 725/706 мс на компьютере, это не нагрузочный benchmark и не Pi. GGUF/HA-токен не нужны, telemetry_stale=true явно показывает отсутствие текущего реального сбора. Процессы/временная БД/логи удалены.

## Воспроизведение

Из core/:

```bash
.venv/bin/python -m pytest -q tests/test_analytics_engine.py tests/test_analytics_service.py tests/test_migrations.py
.venv/bin/python checks/check_analytics.py --output ../docs/reports/task-20-new-run.json
```

Второй сценарий запускается отдельно от pytest: разрешён только синтетический loopback HTTP, собственные временные ключ/БД в .pytest_cache, рабочий .env не читается. Отчёт не перезаписывается. Тяжёлых зависимостей и моделей нет; общий диск всё равно проверять перед следующей работой.
