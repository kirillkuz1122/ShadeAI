## Принятый программный дизайн

- Календарные напоминания отдельны от delivery hints TASK-21: прежний opt-in не расширять. CALENDAR_REMINDERS_ENABLED=false/lead10мин, только confirmed+busy/non-all-day и свежий snapshot. GET deterministic schedule/validate по ID, без title/location; scope+eventID/revision+lead дают устойчивый ID после рестарта. Окно24ч/grace5мин/до50предстоящих; при переполнении явно не считать выборку полной.
- Android: отдельный opt-in/permission, минимальные ID/due/expiry/revision в prefs (без ключа/текста), AlarmManager exact при доступе Android12+, periodic WorkManager15мин для сверки/восстановления. AlarmReceiver goAsync делает короткую проверку Core перед generic OS-notification; отменённое/revision-changed/stale/истёкшее не показывать. Недоступный Core — ограниченный retry в grace, не обещать доставку офлайн в минуту. На новом scope/настройках выключение/очистка, старые opt-in не переносить. Старые alarm/receipts ограничить; NotificationManager+receipt не атомарны, стандартная идемпотентность не равна exactly-once при аварии. Если exact permission нет — явно показать задержанный fallback, критерий точности остаётся открытым.
- Режим встречи: глобально defaultdisabled/allowed switch.*=[] (до5), пользователь отдельно подтверждает конкретное событие/revision/время и цели с policy-scope. Только выделенные DND-switches, без произвольных params. Общее владение устройством для пересекающихся встреч; последняя встреча восстанавливает исходное off, исходное on не присваивается себе. Активное окно≤8ч, DATE/tentative/stale не активируют режим.
- Каждая HA-команда только через execute_command/audit, durable applying/restoring до сети, без DB-транзакции во время HTTP. Истечение/отмена/изменение календаря отменяют будущую активацию и снимают только подтверждённое владение. При stale уже активное держится лишь до сохранённого конца, новые встречи не начинают. По завершении сравнить state+context/наблюдавшиеся timestamps, не затирать наблюдённое ручное изменение. После аварии in-flight→unknown, не повторять команды. Удалённая из allowlist цель не управляется даже для восстановления, нужен ручной разбор.
- Контекст HA официально есть в state object ([документация](https://www.home-assistant.io/docs/configuration/state_object/)); last_updated не меняется при одинаковом состоянии. Это наблюдаемая защита, не возможность узнать ненаблюдаемое намерение пользователя или атомарно связать физический мир с REST. Raw user_id/context/attrs не сохранять, только необходимый хеш context и timestamps. Проверить реальные DND-сущности отдельно.
- Новая миграция для планов/общего владения/аудита режима; protected API+Web управления, Android API/экран напоминаний. Синтетические lifecycle/отмена/restart/пересечения/ручные изменения и loopback; системный Alarm/notification проверить на одноразовом AVD при измеренном запасе RAM/диска.

## Уточнение дизайна после начала реализации

Напоминания **не** добавляются в LocalHint/TASK-21 и не требуют миграции его ID. Новый GET calendar/reminders выводит расписание из durable CalendarEvent: scope+event.id/revision+lead → rmd_32hex. GET validate этого ID заново проверяет свежесть/статус/ревизию; due/expiry ограничены5мин после заданного due (не после начала встречи), окно24ч. До50предстоящих, overflow явно возвращает пустую неполную выборку. На Android отдельный opt-in/политика/минимальные alarm metadata; старый hint-optin сохраняет прежний смысл. Periodic worker сверяет ближайшие24ч, не считается точным таймером; exactAlarm/goAsync validation делает показ, недоступность Core даёт retry лишь в grace. При stale сохранять уже назначенные alarm metadata, но не создавать новые; в момент alarm всё равно проверять Core. При выключении/смене scope — отменить свои alarms/notifications. Receipts предотвращают обычный повтор, атомарность с NotificationManager не обещается.

Core-расписание уже написано: calendar.snapshot вынесен в сервис,2 новых GET, defaultdisabled settings/lead.20 тестов reminders+calendar-service прошли (7новых), ruff; пока **нет** Android Alarm-кода, режима встречи, новых полных проверок/коммита24. API-контракт ещё нужно дополнить до коммита.

Планы режима: MeetingPlan по event_id хранит scope/revision/starts/ends/targets/status и started_targets. Started-target сохранять для того же scope/ревизии: после завершения/unknown/ручного ack тот же переход не активируется заново; при новом явном согласии на изменившееся событие можно новую попытку. Общий MeetingLease по switch entity хранит generation, members(event_ids), state waiting/applying/active/external/restoring/completed/unknown, исходное состояние, хеш context/наблюдённые timestamps, audit ID/reason/retry_at. Пересечения встреч используют один lease, последняя снимает owned-mode. Уже on — external, без команды и восстановления. In-flight после рестарта unknown, без повтора. Пользователь может явно ack unknown-generation **без команды**, старые started-target не сбрасывать. Новые команды только для enabled/current consent/fresh confirmed busy non-DATE≤8ч; активный lease при stale живёт лишь до сохранённого конца. Изменение/отмена/другой calendar scope снимают участие; удаление устройства из allowlist запрещает и restore (manual review). API disable не блокировать на HTTP; новые checks перед записью applying, после неё отмена не обещает отозвать запрос. Только общая execute_command/audit, сеть вне DB.

HAState можно расширить optional context.id (без user_id/parent_id в модели/БД); для ownership использовать ответ изменённых состояний + отдельный текущий state, ctx hash/timestamps. Это наблюдаемая защита, не атомарная причинность REST: внешняя одинаковая команда без state/context-изменения не видна. Для restore менять только состояние, совпадающее с наблюдавшимся owned-result. Отсутствие context/подтверждения — не включать/unknown, не угадывать. Ошибки/журнал только фиксированные, без params/Calendar-текстов. Официальные источники context/REST изучены, ссылки выше.
