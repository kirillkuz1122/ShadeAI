# Shade AI — Android-клиент

Клиент Shade AI на Kotlin + Jetpack Compose: настройки адреса/ключа, проверка Core и авторизации, служебная тестовая отправка. Доступ Android, выбор источников и фильтр до Room реализованы в TASK-10; программная часть форматов/UUID/буфера TASK-11 проверена на эмуляторе; приёмка на телефоне открыта, повторы и журнал — TASK-12/13. TASK-09 реализована и проверена на эмуляторе без физического телефона; аппаратная приёмка остаётся открытой. [Отчёт TASK-09](../docs/reports/task-09.md).

## Сборка

Нужны **JDK 17**, Android SDK Platform 35 и Build Tools 34.0.0. Проект использует AGP 8.7.3, Kotlin 2.0.21 и Gradle Wrapper 8.10.2; [совместимость AGP](https://developer.android.com/build/releases/agp-8-7-0-release-notes).

В Android Studio (Ladybug или новее): откройте `android/`, выберите JDK 17 для Gradle, установите SDK-компоненты через SDK Manager, затем соберите `app` или запустите на устройстве. Подходит Android 8.0/API 26 и новее.

Можно собрать из терминала, без установки IDE:

```bash
cd android
# JAVA_HOME должен указывать на JDK 17, ANDROID_HOME — на установленный SDK.
./gradlew :app:assembleDebug :app:lintDebug --no-daemon --max-workers=2
```

Для локальных инструментов, установленных при TASK-03 в этом проекте (Linux):

```bash
cd android
env -u ANDROID_SDK_ROOT \
JAVA_HOME=/usr/lib/jvm/java-17-openjdk \
ANDROID_HOME="$PWD/.gradle/sdk" \
ANDROID_USER_HOME="$PWD/.gradle/android-home" \
GRADLE_USER_HOME="$PWD/.gradle/user-home" \
./gradlew :app:assembleDebug :app:lintDebug --no-daemon --max-workers=2
```

SDK и кэш Gradle в `.gradle/` не входят в git и не появятся при новом клонировании. На другом компьютере установите инструменты через [Android Studio / Command-Line Tools](https://developer.android.com/studio) и укажите свой путь SDK. `local.properties`, если используется, тоже не коммитится. Если унаследованная `ANDROID_SDK_ROOT` указывает на другой SDK, Gradle откажет из-за конфликта: пример выше удаляет эту переменную только для команды сборки.

Debug APK: `app/build/outputs/apk/debug/app-debug.apk`. Установка на подключённый телефон:

```bash
adb install -r app/build/outputs/apk/debug/app-debug.apk
adb shell am start -n com.shadeai.app/.MainActivity
```

DTO health синхронизирован с TASK-06. В TASK-09 Bearer добавлен к защищённым запросам UI и NotificationListener, но health выполняется без ключа. Управления устройствами в Android пока нет.

## Настройки и проверка подключения (TASK-09)

1. Запустите [Shade Core](../core/README.md) на компьютере или Pi. Введите его доверенный локальный адрес: http(s)://host:port либо с /api/v1/. Путь нормализуется к /api/v1/. Логин/пароль, query, fragment, другой путь и пробелы внутри адреса запрещены; значение ошибки не выводит исходный URL.
2. Введите SHADE_API_KEY из локального файла настроек Core: не менее 32 печатных ASCII-символов без пробелов. Поле скрыто, после сохранения очищается. Нажмите «Сохранить и проверить».
3. Проверяются независимо открытый health и защищённый GET notifications?limit=1. «Ключ принят» отделён от статуса Core/БД/HA. 401 означает отказ ключа Core; HA_AUTH_FAILED в health — отдельная ошибка токена HA. Отказ HA не мешает доставке уведомления в Core. 5xx, redirect, таймаут, TLS и отсутствие соединения отображаются безопасными сообщениями, без текста исходного исключения/ответа.
4. «Отправить тестовое уведомление» отправляет одну служебную запись Ozon без личных данных, со свежим UUID event_id и временем. Для неё не нужен доступ к уведомлениям телефона. Stored/duplicate показываются как сохранение с ID; skipped — как пропуск по правилам Core. Новый ручной клик — отдельная служебная запись, автоматического повтора нет.
5. Адрес и зашифрованный ключ сохраняются после остановки процесса. Пустое поле ключа оставляет прежний ключ только для того же нормализованного адреса. Для нового адреса введите ключ заново. «Удалить ключ» удаляет сохранённый шифротекст; последующие защищённые запросы без ключа не отправляются. Удаление не отзывает уже отправленный запрос и ключ на самом Core.

**Хранение:** SharedPreferences MODE_PRIVATE сохраняет адрес и AES-GCM шифротекст с IV; AES-ключ находится в Android Keystore, исходный SHADE_API_KEY на диск не записывается. AAD привязывает шифротекст к адресу. При повреждении хранилища/недоступном Keystore показывается ошибка без автоматического сброса; удалите ключ и введите заново. Удаление логическое, защиты от компрометированного устройства/памяти процесса не заявляется. Настройки не переносятся на другое устройство автоматически.

Автоматический Android backup выключен (allowBackup=false); XML-правила исключают файлы, БД и preferences из cloud backup и device transfer для соответствующих API. Результат системного backup на устройствах разных производителей ещё не проверялся. Правила нужны и для будущего Room-буфера: он не должен попадать в облако.

Состояние экрана хранится в ConnectionViewModel/StateFlow и собирается через collectAsStateWithLifecycle. Редактирование отменяет предыдущую проверку и не применяет её запоздалый результат. API-клиент получает снимок адреса/ключа, использует общий транспорт без хранения idle-соединений, connect/read/write/call timeout 3/5/5/10 секунд, без redirect, proxy и автоматических повторов. HTTPS сохраняет штатную проверку сертификатов. Адрес должен принадлежать вашей LAN/доверенной VPN; частная сеть DNS/IP автоматически не проверяется. Для HTTP действует точный список Network Security Config ниже.

Доступ к уведомлениям и выбор источников описаны ниже в TASK-10. Форматы, сохранённые UUID и очистка отправленного реализованы в программной части TASK-11 ниже. Надёжные повторы реализованы в TASK-12 ниже; строки старой Room v1 сохраняют серверный отпечаток полей. Timestamp — Instant без общего SimpleDateFormat. Успешный служебный POST не подтверждает перехват/фоновые повторы с телефона.

## Доступ к уведомлениям и источники (TASK-10)

Откройте «Уведомления и источники» на экране подключения. Здесь показан фактический доступ Android и есть переход «Настроить доступ Android». На системном экране выдайте или отзовите разрешение для Shade AI. После возврата состояние обновляется; кнопка «Обновить состояние» повторяет проверку. Выданное разрешение ещё не означает, что ОС подключила сервис или что доставка надёжна.

По умолчанию **все источники выключены**, в том числе при обновлении старого приложения с фиксированным allowlist. Отметьте нужные сервисы: Ozon (`ru.ozon.app.android`), Wildberries (`com.wildberries.ru`), Яндекс Go (`ru.yandex.taxi`). Каталог ограничен политикой TASK-05; он не сканирует установленные приложения и допускает предварительный выбор ещё не установленного сервиса. Core должен разрешать тот же источник в NOTIFICATION_ALLOWED_APPS. Произвольные приложения, банки, SMS и мессенджеры включить нельзя. Выбор хранится отдельно от ключа, сохраняется сразу и переживает остановку процесса.

Android выдаёт сервису доступ ко всем уведомлениям, но Shade проверяет разрешение и выбранный источник **до INSERT в Room**. Пустые title/text, слова с началами «код», «парол», «пин» и отдельные code/otp/pin/password/cvv/cvc отбрасываются. Это консервативное правило TASK-05, а не гарантия распознавания любого секрета. Дополнительно исключены ongoing, foreground service, group summary и local-only уведомления. Системная заглушка Android 15 о скрытом чувствительном содержимом также отбрасывается: используется локализованная строка ОС с английским fallback. Дополнительный доступ к скрытым данным не запрашивается. Текст и исключения не пишутся в логи. Расширенный текст, InboxStyle и ticker поддержаны в TASK-11; MessagingStyle намеренно пропускается как переписка.

При отключении источника удаляются его локальные записи, включая отправленные. Проверка доступа/выбора повторяется перед отправкой старого буфера; запрещённая pending-запись удаляется. Сохранение выбора и отправка упорядочены общим Mutex: уже начатый запрос может завершиться до подтверждения отключения (таймаут до 10 секунд), после подтверждения новый запрос из отключённого источника не начинается. При отзыве разрешения сервис прекращает приём; буфер очищается при следующей проверке в UI или подключении сервиса. Если ОС убила процесс, немедленное удаление файла БД не гарантируется. Уже переданное в Core не удаляется, отправку задним числом отменить нельзя.

Сервис ждёт onListenerConnected, отменяет задачи при disconnect/destroy. Разбор обновлений, UUID и ограниченный буфер реализованы в TASK-11; отправкой и повторами теперь управляет WorkManager (TASK-12 ниже). Ручная кнопка теста подключения — отдельная служебная отправка без перехвата и не зависит от выбора источников.

[Отчёт TASK-10](../docs/reports/task-10.md) содержит результаты и границы проверки. API доступа и системный переход следуют [NotificationManager](https://developer.android.com/reference/android/app/NotificationManager#isNotificationListenerAccessGranted(android.content.ComponentName)); lifecycle и декларация сервиса — [NotificationListenerService](https://developer.android.com/reference/android/service/notification/NotificationListenerService). На API 26 проверяется точное имя компонента в enabled_notification_listeners; на API 27+ используется NotificationManager. В текущей сессии проверен API 35.

## Форматы, идентичность и локальный буфер (TASK-11)

NotificationReader выбирает расширенный заголовок (или обычный), а текст — по приоритету BigText → строки InboxStyle через перевод строки → обычный text → ticker. Допускается только заголовок или только текст. Все доступные варианты, subtext и ticker проверяются на признаки секретов **до выбора полей**, без обрезки. Неверные типы Bundle, более 100 строк, суммарно более 32768 кодовых единиц кандидатов и превышение итоговых 512/8192 кодовых единиц title/text приводят к пропуску. Чужие сообщения EXTRA_MESSAGES не читаются; источник должен оставаться в каталоге TASK-10. Это консервативные пределы Kotlin UTF-16, не расширение серверных лимитов.

Для системного ключа StatusBarNotification.key хранится SHA-256, исходный tag/key на диск не записывается. Последняя принятая версия title/text сравнивается по хешу нормализованных полей. Повтор с тем же ключом и содержимым не создаёт строку и не меняет прежний postTime, даже если время повторного callback изменилось. Изменение title/text создаёт отдельную неизменяемую версию с новым UUID; две разные Android-карточки имеют отдельные версии. После onNotificationRemoved последующая публикация того же ключа начинает новую историю. При подключении ОС сверяются активные ключи и помечаются исчезнувшие; старые активные уведомления принудительно не импортируются. Потерянные во время force-stop события целиком восстановить этим нельзя.

UUID новых событий сохраняется **до отправки** вместе с title/text/postTime и передаётся как event_id. Повторная отправка использует тот же payload. После помещения в буфер поля не переписываются; обновление — новая версия, поэтому повтор UUID не конфликтует с изменённым текстом на Core.

Room v3 хранит статусы (v2 обновляется без удаления данных):

| Статус | Значение |
|---|---|
| PENDING | Сохранено, подтверждения Core нет; сюда входит ожидание ключа/отмена запроса |
| FAILED | Попытка не получила корректного подтверждения; дальнейшее действие определяется lastError и состоянием очереди |
| SENT | Core ответил stored/duplicate с положительным ID; обработка AI этим не подтверждается |
| SKIPPED | Core ответил skipped с id=null; окончательный пропуск без повтора |
| REJECTED | Core отклонил конкретный payload (400/409/413/422); автоматического повтора нет |

Неизвестный/неполный ответ не считается доставкой. Классификация ошибок, backoff и автоматическое восстановление сети — в разделе TASK-12 ниже. Сырые исключения/ответы в Room не сохраняются. Список статусов в UI — TASK-13.

Запись выполняется отдельно от сетевого ожидания. Сессия listener содержит последовательный обработчик callbacks; при disconnect/destroy обработчик и канал отменяются. Отправка сохранённого выполняется независимо через WorkManager с повторной проверкой доступа/источника. Сохранённое до отмены остаётся неподтверждённым и имеет прежний UUID. В памяти не удерживаются сырые StatusBarNotification/RemoteViews. Смена выбора источников упорядочена с отправкой, а новая запись не ждёт сетевой timeout.

Пределы: не более 1000 строк буфера и 2000 записей метаданных последней версии; до 128 callbacks в памяти; список одной отправки — до 100 строк. Переполнение callback-канала пропускает новые callbacks; При заполнении Room новое событие пропускается до освобождения места. Неподтверждённое хранится до 7 дней, SENT/SKIPPED/REJECTED — до суток после подтверждения; метаданные дедупликации — до 7 дней, при лимите сначала удаляются неактивные. Очистка выполняется при проверке настроек, подключении/синхронизации и новой записи, без обещания удаления ровно по таймеру при остановленном процессе. После очистки метаданных старый повтор может снова считаться новой версией. WorkManager продолжает очередь порциями до 100 строк (TASK-12). Это ограничения текущего этапа, не гарантия доставки всех событий при любой нагрузке.

### Обновление Room v1 → v2

Схемы [v1](app/schemas/com.shadeai.app.data.db.AppDatabase/1.json) и [v2](app/schemas/com.shadeai.app.data.db.AppDatabase/2.json) экспортируются и хранятся в Git. [Миграция](app/src/main/java/com/shadeai/app/data/db/BufferMigrations.kt) сохраняет старые ID, тексты, postTime и счётчик AUTOINCREMENT; sent=1 становится SENT, остальное PENDING. Создание/завершение старых строк датируется обновлением. Destructive fallback удалён; при конфликте миграция откатывается, старый буфер сохраняется. Не заменяйте ошибку очисткой данных, если в приложении есть нужный буфер.

У старых строк eventId/sourceKey остаются null: исходный системный ключ неизвестен, а выдача нового UUID могла бы создать дубль вместо прежнего серверного отпечатка. Старые pending отправляются без event_id; новые используют UUID. Дедупликацию callbacks со старой историей v1 достоверно восстановить нельзя. Сначала сохраните нужные данные/сделайте локальную резервную копию; автоматический cloud backup по-прежнему выключен. SQL-удаление не гарантирует уничтожение старых страниц БД/WAL или копий.

### Проверки TASK-11

[Отчёт и границы приёмки](../docs/reports/task-11.md). Из android/ с JDK/SDK из раздела сборки:

```bash
./gradlew -PnotificationFixture=true \
  :app:assembleDebug :app:testDebugUnitTest :app:lintDebug \
  :app:connectedDebugAndroidTest :notification-publisher:assembleAllowedDebug \
  --no-daemon --max-workers=2
```

Для сквозного сценария нужен свежий checks/core_server.py (запуск из корня репозитория как в TASK-10), AVD emulator-5554 без установленного коммерческого Ozon и завершённые Gradle-тесты. Затем из корня:

```bash
python android/checks/check_buffer.py
```

Скрипт проверяет qemu, отказывается заменять установленный пакет, сбрасывает данные debug-приложения Shade только в эмуляторе, настраивает тестовый Core через UI, выбирает Ozon и выдаёт доступ через adb. Проверяются настоящие системные BigText/Inbox/ticker/только заголовок, код в скрытом варианте, повторы/изменения/cancel/repost, force-stop и повторное подключение. Сеть Core сначала отключается, затем восстанавливается с явным переподключением listener; автоматическая реакция на восстановление Wi-Fi этим не подтверждается. UUID/payload/время сравниваются со снимком Room и Core. Тестовый издатель, reverse и доступ убираются в finally. Снимок синтетической БД лежит в android/.gradle/task11-checks/snapshot, не в Git. После проверки остановите тестовый Core/AVD. Физический критерий TASK-11 остаётся открытым до телефона; сейчас его не требуется предоставлять.

## Локальный транспорт

[Network Security Config](app/src/main/res/xml/network_security_config.xml) запрещает HTTP по умолчанию и разрешает его только для точных адресов: `192.168.1.100`, `10.0.2.2`, `127.0.0.1`, `localhost`, `shade.local`. Это адрес Core по умолчанию и локальная разработка; поддомены не разрешаются автоматически. HTTPS использует штатную проверку сертификатов Android.

Для другого IP сервера добавьте именно этот адрес в `domain-config` файла выше и пересоберите APK либо используйте HTTPS с доверенным сертификатом. Не включайте HTTP глобально и не отключайте проверку TLS. Правила конфигурации — в [документации Android](https://developer.android.com/privacy-and-security/security-config).

Для эмулятора используйте `http://10.0.2.2:8000/api/v1/`, для USB-подключения можно перенаправить порт:

```bash
adb reverse tcp:8000 tcp:8000
```

После перенаправления адрес в приложении: `http://127.0.0.1:8000/api/v1/`.

## Проверки без физического телефона

JVM-тесты URL/HTTP и Android-тесты Keystore/настроек используют зависимости только test/androidTest. Для эмулятора API 35 выполните с теми же JDK/SDK из раздела сборки:

```bash
./gradlew :app:testDebugUnitTest :app:connectedDebugAndroidTest :app:lintDebug --no-daemon --max-workers=2
```

Android-тесты используют отдельный preferences-файл, не заменяют сохранённый ключ UI. В эмуляторе проверяются реальные Android Keystore и Network Security Config, но не поведение конкретного физического телефона.

## Надёжная доставка и повторы (TASK-12)

Отправка сохранённого буфера вынесена из listener в [CoroutineWorker](app/src/main/java/com/shadeai/app/service/NotificationDeliveryWorker.kt) на WorkManager 2.10.1. В БД WorkManager нет текста уведомлений, URL или ключа: worker читает текущие настройки/Room при запуске. Новое событие, запуск приложения, подключение listener и появление сети ставят работу; уникальная цепочка ограничивает параллельные отправки. Один worker берёт до 100 строк и работает до 45 секунд, затем ставит следующую порцию/задержку. Общий Mutex сохраняет порядок отправки и изменения выбора/настроек; запись новых уведомлений сеть не ждёт.

При полном отсутствии сетей HTTP не начинается, запись остаётся PENDING. WorkManager ждёт с собственным backoff, появление сети заменяет ожидающую работу немедленной проверкой. Не требуется INTERNET/VALIDATED: отсутствие внешнего Интернета само по себе не запрещает локальный HTTP. Наличие сети ещё не доказывает доступность Core; серверный адрес и Network Security Config проверяются как раньше.

| Результат | Действие очереди |
|---|---|
| stored/duplicate с положительным ID | SENT, переход к следующей строке |
| skipped с id=null | SKIPPED, переход к следующей строке |
| IOException/timeout, HTTP 408/425/429/5xx | FAILED, задержка всей очереди: 30 с, 1 мин, 2 мин и далее до 6 ч |
| HTTP 401/403, перенаправление/ошибка адреса/другие 4xx, TLS/ошибка настроек/неверный receipt | Пауза очереди до сохранения настроек подключения |
| HTTP 400/409/413/422 | REJECTED только этой строки; следующая не блокируется |
| Ключ отсутствует | PENDING с категорией credentials; ожидание сохранения настроек |

Задержка/число последовательных ошибок и пауза хранятся в единственной строке delivery_control. UUID/payload неизменяемы; повтор после потери ответа даёт duplicate на Core. У каждой строки attempts (завершённые попытки, включая проверку отсутствующего ключа) и lastError (только безопасная категория, например http_401/network). Результат строки и состояние очереди записываются одной транзакцией. Сбой этой транзакции передаётся worker для backoff; успешный HTTP без сохранённого подтверждения повторяется с прежним UUID.

Сохранение/удаление ключа создаёт случайную несекретную revision и упорядочено с активной отправкой. Новая revision снимает паузу/backoff; новые уведомления, рестарт и сетевые callbacks сохранённую серверную задержку/401 не сбрасывают. Чтобы повторить после исправления Core или сертификата, снова нажмите «Сохранить и проверить». Программной кнопки повтора отдельного REJECTED пока нет; журнал реализован в программной TASK-13 ниже. После изменения URL оставшийся буфер отправляется на выбранный пользователем Core; ключ автоматически между адресами не переносится.

### Миграция и пределы фоновой работы

Новая миграция v2→v3 добавляет attempts/lastError и delivery_control. Схема [v3](app/schemas/com.shadeai.app.data.db.AppDatabase/3.json) хранится рядом с v1/v2. UUID, тексты, ID, sequence, статусы и heads сохраняются; миграция v1→v2 не менялась. Destructive fallback отсутствует.

Каждые 15 минут запланирован восстановительный worker, который будит уникальную очередь. Он страхует гибель процесса между INSERT и постановкой работы, а также событие на границе завершения worker. Это минимальный интервал планирования, **не SLA**: Doze, квоты и ограничения производителя могут откладывать работу. Foreground service, точные таймеры, обход энергосбережения и постоянный wake lock приложения не используются. После пользовательского force-stop Android блокирует работу до следующего запуска приложения. Отсутствующие во время остановки callbacks восстановить нельзя. Физический телефон/экран off/ограничения производителя ещё входят в приёмку TASK-13; гарантии мгновенной доставки этим этапом не даны.

## Журнал уведомлений (программная TASK-13)

На экране подключения откройте «Журнал уведомлений». Он показывает сохранённые на этом устройстве записи: источник, время события, заголовок/текст, статус доставки и безопасное пояснение последней ошибки. Нажмите карточку для полного текста, UUID, времени сохранения/завершения и числа завершённых попыток. Состояние SENT означает получение Core; это не результат AI-обработки.

Фильтры: все, в очереди (PENDING/FAILED), доставлено, пропущено, отклонено. Страница содержит до 50 записей; «Более ранние»/«Более новые» используют границу ID, поэтому новые уведомления не сдвигают уже открытую старую страницу. При удалении всей открытой страницы журнал возвращается к началу. Счётчики относятся ко всему локальному буферу, включая записи на других страницах.

Строки, счётчики и delivery_control читаются одним снимком Room; изменения отслеживаются через InvalidationTracker, без опроса сети. Подписка работает только при открытом журнале и видимом приложении. При уходе со страницы/в фон наблюдение отменяется, тексты удаляются из UI-state. В SavedState попадают только маршрут и ID открытой карточки, без текста, ключа или полного объекта уведомления. Перед чтением выполняется общая очистка доступа/источников/сроков. Ошибка чтения очищает прежние данные и предлагает обновить журнал.

Открытие/обновление журнала не снимает backoff или паузу 401 и не запускает ручной повтор отдельного REJECTED. Верхний блок показывает ожидание, минимальное время следующей попытки либо необходимость сохранить настройки. Для восстановления после 401 используйте «К подключению» → «Сохранить и проверить». После отключения источника или отзыва доступа при следующей проверке локальная история исчезнет; уже полученное Core остаётся в его БД/вебе до серверной очистки. Это буфер с ограниченным сроком хранения, не постоянный архив и не список всех уведомлений Android.

В веб-деталях теперь показан «Идентификатор события» — UUID отправителя для сопоставления с карточкой Android. Старая запись без UUID обозначена явно. REST API и схема Room v3 не изменялись, новые зависимости не добавлялись.
