# Shade Core

Бэкенд Shade AI на FastAPI. [Контракт API](../docs/api-spec.md), [архитектура](../docs/architecture.md), [задачи](../docs/mvp.md).

## Локальная установка и запуск

Команды выполняются из корня репозитория. Нужен Python 3.11 или новее; чистая установка проверена на Python 3.11.

```bash
cd core
python3.11 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m app.setup
# При необходимости отредактируйте HA_BASE_URL и HA_TOKEN в .env.
python -m uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

- Health: `curl http://localhost:8000/api/v1/health` — доступен без ключа.
- Swagger UI: `http://localhost:8000/docs`.
- Защищённые запросы требуют `Authorization: Bearer <SHADE_API_KEY>`.
- Работа Home Assistant и LLM не требуется для старта. Без HA health сообщает `status: degraded`, `ha_connected: false`; LLM пока заглушка.

`requirements.txt` содержит зависимости приложения, `requirements-dev.txt` добавляет pytest и ruff. Прямые зависимости закреплены на проверенных версиях; транзитивные зависимости полностью не зафиксированы. LLM-зависимости остаются отдельно в `requirements-llm.txt`, для запуска скелета они не нужны.

## Настройки и ключ

Настройки читаются из `.env` в рабочем каталоге, переменные окружения имеют приоритет. Запускайте сервер из `core/`.

`python -m app.setup` копирует шаблон `.env.example`, создаёт локально случайный ключ через `secrets.token_urlsafe(32)` и устанавливает права файла `600`. Команда не выводит ключ. Если `.env` уже существует, остальные параметры сохраняются, корректный ключ не заменяется. Пустое значение и известные заглушки `change-me` / `change-me-to-long-random-string` заменяются случайным ключом.

| Переменная | Назначение |
| :--- | :--- |
| `SHADE_API_KEY` | Обязательный Bearer-ключ: не менее 32 ASCII-символов без пробелов; имя `API_KEY` не используется |
| `DB_URL` | По умолчанию `sqlite+aiosqlite:///./shade.db` |
| `HA_BASE_URL` | Адрес локального HA; по умолчанию `http://127.0.0.1:8123` |
| `HA_TOKEN` | Токен HA; по умолчанию пустой — HTTP в HA не выполняется |
| `HA_TIMEOUT_SECONDS` | Общий бюджет одного HTTP-обмена: 5 секунд, диапазон 0.1..30; ping также ограничен 2 секундами |
| `EVENT_RETENTION_DAYS` | Хранение журнала команд: 90 дней, диапазон 1..365 |
| `LOG_DIR` | Каталог локальных служебных логов; по умолчанию ./logs |
| `LOG_MAX_BYTES` | Ротация файла: 1 048 576 байт, диапазон 1024..10 485 760 |
| `LOG_BACKUP_COUNT` | Число архивных файлов: 3, диапазон 1..10 |
| `LLM_MODEL_PATH` | Путь к GGUF для будущего подключения LLM |
| `CORS_ORIGINS` | Если задан, JSON-массив адресов; по умолчанию разрешены localhost/127.0.0.1:5173 |
| `NOTIFICATION_RETENTION_DAYS` | Хранение уведомлений: 30 дней по умолчанию, диапазон 1..365 |
| `NOTIFICATION_ALLOWED_APPS` | JSON-список до 100 доверенных служебных пакетов; по умолчанию Ozon, Wildberries, Яндекс Go |

Можно создать файл по другому пути: `python -m app.setup --env-file /путь/к/.env`. Это только путь для настройки: сервер по-прежнему читает `.env` из своей рабочей директории или переменные окружения.

Если ключ отсутствует или некорректен, Core прекращает запуск и предлагает выполнить настройку. Произвольный некорректный ключ команда настройки не перезаписывает: исправьте его вручную либо очистите значение `SHADE_API_KEY` и повторите команду. Символические ссылки вместо файла настройки не принимаются. Если в окружении задан старый/неверный `SHADE_API_KEY`, исправьте или удалите эту переменную: она перекрывает `.env`.

Для настройки веба скопируйте ключ из локального `.env` в поле интерфейса. Настройки URL/ключа и Bearer в Android реализованы в TASK-09 и проверены на эмуляторе; [аппаратная приёмка](../docs/reports/task-09.md) ещё открыта.

## Уведомления (TASK-05)

POST /api/v1/notifications сохраняет допустимое уведомление и возвращает **201/stored**. Повтор — **200/duplicate** с прежним ID; исключённое уведомление — **200/skipped** с id=null и reason=privacy_policy или expired. Заглушка LLM не вызывается, processed_data=null. TASK-15 добавляет отдельную durable-очередь; по умолчанию worker disabled, включаемый diagnostic проверяет конвейер без AI-анализа.

Для повторной отправки предпочтителен стабильный UUID event_id, созданный один раз и сохранённый отправителем вместе с событием. Тот же UUID с другим содержимым даёт 409. Для прежних клиентов без UUID действует отпечаток нормализованных полей app_name/title/text/timestamp/priority. Он не различает два намеренно одинаковых события в один момент: для них нужны разные UUID. ID сервера остаётся целым и не переиспользуется после удаления. [Полный контракт](../docs/api-spec.md#41-уведомления-notifications--реализовано-в-task-05).

GET /api/v1/notifications поддерживает limit (1..200), offset (0..1 000 000) и category, возвращает общий total и страницу по ID в обратном порядке. GET /api/v1/notifications/{id} возвращает запись или 404. Timestamp входа требует часового пояса, нормализуется в UTC; более 5 минут в будущем отклоняется. Лимиты — 512 символов заголовка, 8192 текста, 65 536 байт тела запроса; ошибки не возвращают исходное содержимое.

**Приватность:** по умолчанию разрешены только ru.ozon.app.android, com.wildberries.ru, ru.yandex.taxi. Список можно задать через NOTIFICATION_ALLOWED_APPS, пустой список запрещает всё. Известные пакеты банков, Telegram/WhatsApp и SMS исключены независимо от списка. Уведомление целиком пропускается при словах код*/парол*/пин*/code/otp/pin/password/cvv/cvc в заголовке или тексте: даже код получения доставки пока не сохраняется. Добавляйте только доверенные служебные приложения; это явная политика допуска, а не универсальный классификатор личной переписки. Содержимое пропущенного уведомления не сохраняется и не публикуется в шину событий; SQL-параметры скрыты в диагностике ошибок.

**Хранение:** по умолчанию 30 дней от времени события или серверного получения, по более раннему сроку. Просроченные записи сразу исключены из API, физическая очистка выполняется при старте, каждый час и перед новой записью. Периодическая задача отменяется при завершении приложения; при ошибке повторяет очистку через час без записи содержимого исключения в лог.

**При обновлении старой БД** сначала сделайте копию. Ревизия 0003 сохраняет строки при изменении схемы; затем до приёма запросов Core проверяет старые записи пакетами по 256. Не прошедшие политику, повреждённые, просроченные и повторные удаляются; допустимые нормализуются и получают ключ. Прежние результаты заглушки/JSON очищаются. Логическое удаление не стирает прежние копии и остатки в страницах SQLite/WAL; регламент резервирования остаётся TASK-08. Рабочую БД без копии для пробной проверки не используйте.

## Home Assistant, журнал и логи (TASK-06)

Укажите HA_BASE_URL локального HA без пути, query, fragment и credentials, а HA_TOKEN — его long-lived access token без пробелов. Для изменения настроек перезапустите Core. Пустой токен допускает запуск без HA: health показывает degraded/HA_NOT_CONFIGURED, приём уведомлений доступен. HA_BASE_URL должен принадлежать доверенной LAN/VPN; сетевой периметр автоматически не проверяется. Токены и рабочий .env не коммитить.

Доступные маршруты с Bearer Core:

- GET /api/v1/devices?domain=light — список живых сущностей HA.
- GET /api/v1/devices/light.living_room/state — состояние одной сущности.
- POST /api/v1/devices/light.living_room/command с JSON `{"action":"turn_on","params":{"brightness":200}}` — вызов сервиса с журналированием.
- GET /api/v1/events?limit=100&offset=0&type=command_failed — журнал команд; доступны также фильтры from/to.
- Старый POST /api/v1/ha/action сохранён, помечен deprecated и использует общий аудит. [Точный контракт и ошибки](../docs/api-spec.md#42-устройства-умного-дома--реализовано-в-task-06).

AsyncClient общий на lifespan, закрывается при завершении. Нет автоматических повторов, redirect и системных HTTP-прокси (`trust_env=False`), HTTPS проверяет сертификат. Ответ ограничен 2 MiB и 5000 состояниями. DeviceState и история выбранных датчиков пополняются отдельным сборщиком TASK-14, описанным ниже. REST устройств сохраняет живое чтение без fallback на кэш.

**Надёжность команд:** до сетевой отправки фиксируется pending в SQLite; без этой записи команда не отправляется. Затем та же строка получает success/failed и outcome. accepted означает принятие сервиса HA, а не физическое выполнение. После него Core отдельно читает целевое состояние: при отказе чтения сохраняет успешный ответ с new_state=null/state_observed=false. Если HA мог выполнить запрос, но ответ/финализация потеряны, outcome может быть unknown или accepted. Сохранённый pending при следующем старте превращается в interrupted/unknown без повторной отправки. Перед ручным повтором проверить состояние и журнал; каждый POST создаёт новую попытку.

**Журнал:** events_log хранит только request_id/entity_id/domain/service/status/error_code/outcome, без params, токенов, текстов и ответов HA. GET /events выдаёт только команды HA. Хранение 90 дней, очистка при старте и раз в час, просроченное сразу скрыто из API. Очистка действует на events_log; перед обновлением/изменением срока хранения сделать резервную копию. SQLite/WAL и старые копии не очищаются физически безопасным стиранием.

**Служебные логи:** стандартный logging пишет в LOG_DIR/shade.log и архивы .1–.3. Новый каталог создаётся с правами 700, файлы — 600, включая ротацию; существующий каталог должен иметь подходящие права владельца. По умолчанию до четырёх файлов примерно по 1 MiB; размер считается в UTF-8. Пишутся старт/остановка, ID/статус/код результата и безопасные сообщения обслуживания, без params/текстов/секретов. Uvicorn access/error logs остаются в консоли процесса; их хранение на Pi — TASK-08. logs/ исключён из git и Docker-контекста. Невозможность открыть каталог/файл прерывает запуск, чтобы не терять диагностику незаметно.

Health без Bearer проверяет доступность БД (SELECT 1) и HA: HTTP 200/ok либо 200/degraded при отказе HA; HTTP 503/error при отказе БД. Это не полная проверка целостности БД. Размер включает SQLite и WAL; analytics показывает not_implemented; LLM — not_loaded/loading/ready/безопасный код ошибки, notification_worker — отдельный статус TASK-15. [Контракт диагностики](../docs/api-spec.md#451-get-health--реализовано-в-task-06).

## Миграции БД

Таблицы управляются [Alembic](migrations/): `0001_legacy_schema` фиксирует прежние notifications_raw/events_log, `0002_device_states` добавляет состояния HA, `0003_notification_identity` — ключи повторов, индексы срока хранения и SQLite AUTOINCREMENT уведомлений; `0004_event_journal` — индексы и AUTOINCREMENT журнала. Core выполняет upgrade head в lifespan до приёма запросов. Новая БД создаётся миграциями; create_all не вызывается. Для обновления существующей БД сначала остановите Core и сделайте резервную копию.

Команды из `core/`, с тем же окружением и `.env`, что у сервера:

```bash
python -m alembic upgrade head
python -m alembic current
python -m alembic check
```

Адрес берётся из DB_URL настроек Core, в alembic.ini второго адреса нет. Путь по умолчанию — core/shade.db при запуске из core/. current показывает `0004_event_journal (head)`, check проверяет соответствие модели и схемы. Настройка SHADE_API_KEY требуется и для этих команд. Режим --sql не поддерживается: первая миграция должна прочитать существующую схему.

### Переход с БД скелета

1. Остановите запущенный Core и убедитесь, что `DB_URL` указывает на нужный файл. Миграции выполняйте одним процессом, до запуска сервиса.
2. Если в БД есть данные, создайте согласованную копию SQLite через Backup API, учитывающий WAL. Пример из `core/` использует текущий `DB_URL`, создаёт закрытый каталог backups и не перезаписывает существующую копию:

   ```bash
   python - <<'PY'
   import os
   import sqlite3
   from contextlib import closing
   from pathlib import Path
   from sqlalchemy.engine import make_url
   from app.core.config import settings

   url = make_url(settings.db_url)
   if url.drivername != "sqlite+aiosqlite" or not url.database or url.database == ":memory:":
       raise SystemExit("Нужна файловая SQLite-БД")
   source = Path(url.database).resolve()
   if not source.is_file():
       raise SystemExit("Файл БД отсутствует; для новой установки копия не требуется")
   backup = Path("backups/shade-before-update.db")
   backup.parent.mkdir(mode=0o700, exist_ok=True)
   os.close(os.open(backup, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600))
   with closing(sqlite3.connect(source.as_uri() + "?mode=ro", uri=True)) as db:
       with closing(sqlite3.connect(backup)) as copy:
           db.backup(copy)
   print("Копия сохранена:", backup)
   PY
   ```

3. Выполните `python -m alembic upgrade head`, затем `current` и `check`; после успеха запускайте Core обычной командой. На каждом старте повторный upgrade уже актуальной БД ничего не пересоздаёт.

Пустая БД получает все три таблицы. Существующая БД без версии принимается только при совпадении со схемой скелета: обе прежние таблицы, столбцы, типы, NULL/default, ключи и ограничения. Первая ревизия не меняет прежние таблицы; 0003 использует SQLite batch-перестроение notifications_raw с сохранением полей/ID и добавлением столбцов/индексов. 0004 перестраивает events_log с сохранением полей/ID, добавляя индексы времени/типа и непереиспользуемые ID. Частичная или неизвестная схема отклоняется. При ошибке изменения схемы и версии откатываются транзакцией. Не обходите отказ через stamp head. Последующая проверка приватности старых записей описана выше отдельно от изменения схемы.

`backups/` исключён из git и Docker-контекста. Старые миграции не редактировать после применения: изменение моделей сопровождается новой ревизией (`python -m alembic revision --autogenerate -m "Описание по-русски"`), её дифф проверяется вручную. Откат downgrade может удалять таблицы/столбцы с данными; резервная копия нужна для восстановления. Полный регламент резервирования и развёртывания на Pi остаётся TASK-08.

device_states хранит `entity_id` (TEXT, PK), `state`, `attributes_json` (по умолчанию `{}`), `last_changed` и `last_updated` (UTC). Чтение живого состояния по REST реализовано в TASK-06; TASK-14 пополняет кэш только выбранных датчиков, остальные старые строки кэша удаляются при старте сборщика.

## Docker

После локальной установки и `python -m app.setup` выполните из `core/`:

```bash
docker build -t shade-core:local .
docker run --rm --env-file .env \
  -p 127.0.0.1:8000:8000 \
  --mount type=volume,src=shade-core-data,dst=/data \
  -e DB_URL=sqlite+aiosqlite:////data/shade.db \
  -e LOG_DIR=/data/logs \
  shade-core:local
```

Ключ передаётся при запуске через внешний `.env`; образ содержит только пустой шаблон. `.dockerignore` исключает рабочие `.env`, БД, модели, виртуальные окружения и тестовые артефакты. Образ не устанавливает зависимости тестов и LLM. Том сохраняет SQLite и служебные логи между запусками. Порт в примере доступен с локального компьютера.

В контейнере `127.0.0.1` указывает на сам контейнер. Для HA на другой машине укажите его адрес в локальной сети. Развёртывание на Pi, systemd и доступ клиентов по LAN остаются в TASK-08.

## Проверки

Из `core/` после активации окружения:

```bash
python -m pip install -r requirements-dev.txt
python -m pip check
ruff check app tests migrations
python -m pytest -q
```

Тесты самостоятельно изолируют настройки до импорта приложения: рабочий `.env` не читается, значения Core из окружения заменяются тестовыми. Каждый тест выполняется в отдельном каталоге; API-тест получает отдельную SQLite-БД, применяет настоящие миграции через lifespan приложения и освобождает движок на том же event loop. Тесты миграций отдельно проверяют пустую/старую БД, сохранение данных, повторный upgrade, несовместимые схемы, откат при сбое и CLI Alembic.

Home Assistant заменён на `httpx.MockTransport`: тестируются успешные ответы, отсутствие соединения и HTTP-ошибки. DNS и реальные TCP-соединения запрещены; попытка такого запроса провалит тест даже при перехваченном исключении. HA и LLM для pytest запускать не нужно, ключ вручную задавать не требуется.

Временные каталоги создаются в игнорируемом `core/.pytest_cache/` и удаляются после завершения pytest. Для новых API-тестов используйте fixtures `client`, `auth_headers` и `ha_mock` из [tests/conftest.py](tests/conftest.py); добавляйте необходимые маршруты и сценарии в mock. В этих fixtures используются общие настройки приложения, поэтому несколько TestClient одновременно в одном процессе не предусмотрены.

Результаты: [TASK-01](../docs/reports/task-01.md), [TASK-02](../docs/reports/task-02.md), [TASK-04](../docs/reports/task-04.md), [TASK-05](../docs/reports/task-05.md), [TASK-06](../docs/reports/task-06.md). В TASK-06 проходят 126 тестов, в том числе ошибки/таймауты HA, журнал, отказ БД до/после отправки, восстановление pending и ротация логов. Инференс, Android, реальные устройства HA и Raspberry Pi этими тестами не проверяются.


## Телеметрия HA (TASK-14)

Сборщик работает внутри одного процесса Core. Использовать один Uvicorn worker: несколько независимых сборщиков для одной SQLite-БД не поддерживаются. Новая зависимость `websockets==17.1` закреплена явно; она уже входила в uvicorn[standard] локального окружения. После обновления зависимостей перезапустить Core; новая миграция **0005_sensor_history** применяется до API. Перед обновлением сделать копию остановленной БД по разделу миграций.

В локальном `.env` явно выбрать только нужные числовые/бинарные датчики:

```dotenv
HA_TELEMETRY_ENTITIES=["sensor.room_temperature","binary_sensor.hall_motion"]
SENSOR_RETENTION_DAYS=90
SENSOR_HISTORY_MAX_ROWS=100000
```

Также нужны HA_BASE_URL и HA_TOKEN из раздела HA. Изменения требуют перезапуска. По умолчанию `[]`: сбор выключен, сетевых WS-подключений нет. До 100 датчиков, домены sensor/binary_sensor; числовые значения должны быть конечными, бинарные — on/off, unknown/unavailable допускаются. Текстовые и timestamp-сенсоры пока не поддерживаются. Не выбирайте датчики с персональным содержимым. Фильтр применяется до записи и хранения текущих атрибутов; сохраняются только unit_of_measurement/device_class/state_class, без friendly_name/context/old_state.

Сборщик подписывается на state_changed, получает baseline через get_states и атомарно пишет DeviceState, sensor_history, checkpoint и закрытие gap. Снимок имеет источник ha_snapshot и не является событием из прошлого; живое изменение — ha_state_changed с временем HA time_fired, отдельно записано локальное observed_at. Удалённая/не видимая в снимке сущность получает state=null в истории и удаляется из кэша. Повторы внутри сессии отбрасываются; регресс времени HA вынуждает пересинхронизацию. Текстовые/неверные выбранные состояния закрывают сессию с HA_BAD_SENSOR_STATE; исправьте выбор или интеграцию HA.

При разрыве, ошибке БД или остановке открывается telemetry_gaps. Начало — последний durable checkpoint (снимок/pong каждые 30 с), при аварийном рестарте тот же checkpoint восстанавливает консервативную границу. До успешного снимка кэш stale. Переходы во время отключения/начальной синхронизации не выдумываются: они покрыты gap. После переподключения сохраняется новый снимок. Зафиксированный на диск pong подтверждает поток, а не измерение датчика. До первого наблюдения сущности непрерывность не гарантируется; unknown/unavailable и пропуски будущий алгоритм должен учитывать отдельно.

Backoff соединения — 1→60 с + jitter до 20%, сброс после 60 с устойчивого соединения. После auth_invalid/401/403/отказа прав сбор приостанавливает сеть до исправления настроек и рестарта Core. HA-команды по-прежнему без автоповтора. TLS проверяется, proxy/redirect/compression отключены. Сырые кадры и исключения библиотек не логируются; только безопасный код. Порог WS-очереди 16 кадров, сообщение до 2 MiB, снимок до 5000 доступных сущностей, ожидание ответа до HA_TIMEOUT_SECONDS, не более 256 промежуточных событий. Очень большой HA сверх этих пределов требует отдельного пересмотра лимитов; молчаливого частичного baseline нет.

SENSOR_RETENTION_DAYS — 1..365, SENSOR_HISTORY_MAX_ROWS — 1000..500000. Очистка запускается при старте/записи/прикладном pong; при отключённом сборе или auth-паузе — раз в минуту. При недоступном HA — на попытках переподключения. Максимум 1000 последних интервалов gaps и 100 текущих состояний. Снятие сущности с выбора с перезапуском удаляет её кэш и историю; пустой список удаляет всю историю датчиков. Лимит истории использует окно ID, после удаления старых строк фактических строк может быть меньше настройки. SQLite переиспользует освободившиеся страницы: размер файла не обязан сразу уменьшиться, это логическое ограничение строк, не безопасное физическое стирание/квота файла. Резервные копии сохраняются отдельно; аппаратная эксплуатация — TASK-08/27.

Защищённые read-only API: GET /api/v1/telemetry (состояние/выбранный кэш), /telemetry/history?entity_id=sensor.room_temperature&limit=50&offset=0, /telemetry/gaps. Они читают БД даже при недоступном HA, а /devices продолжает читать живой HA. Подробные поля/ошибки/границы — [контракт](../docs/api-spec.md#426-телеметрия-ha--task-14). Экран телеметрии Android/Web этой задачей не добавляется.

Проверки из `core/`:

```bash

.venv/bin/ruff check app tests migrations checks
.venv/bin/python checks/check_telemetry.py
```

Последняя команда — отдельный loopback-стенд, вне обычного pytest с запретом TCP. Он поднимает синтетический HA и два последовательных запуска Core на случайных локальных портах, создаёт случайные тестовые ключи и отдельную SQLite в игнорируемой .pytest_cache/task14-loopback-*, проверяет события/reconnect/пропуски/missing/auth/restart/302/отсутствие сырых атрибутов и ключей в БД/логах. Рабочие .env/HA/БД не читаются; временный каталог/серверы удаляются/останавливаются. Нельзя считать этот стенд проверкой физического HA или длительным накоплением данных на Pi. [Отчёт TASK-14](../docs/reports/task-14.md).


## Очередь обработки уведомлений (TASK-15)

После backup остановленной БД новая ревизия **0006_notification_processing** добавляет processing_status/attempts/error_code/started_at/finished_at и индекс к notifications_raw. Исходные данные и ID сохраняются. Старые строки получают pending/0; прежний is_processed или JSON заглушки не выдаются как результат нового worker. При обработке используются существующие extracted_data_json/is_processed; старые ревизии не редактируются. Откат 0006 удаляет метаданные очереди и сохраняет AUTOINCREMENT/прежние столбцы; после нового upgrade задания снова pending, вычисления могут повториться.

Настройки (применяются после перезапуска):

```dotenv
NOTIFICATION_PROCESSOR=disabled
NOTIFICATION_QUEUE_SIZE=64
NOTIFICATION_PROCESSING_TIMEOUT_SECONDS=30
NOTIFICATION_SHUTDOWN_SECONDS=5
```

`disabled` — нормальное начальное состояние без модели: новые записи остаются pending. Для **технической проверки**, без распознавания текста, явно выбрать diagnostic. Тогда сохраняется только `{"processor":"diagnostic","llm":false}`, category=null. Web пишет «Проверка очереди завершена» и явно сообщает, что AI-анализ не выполнялся. Загрузка LLM/извлечение — TASK-16/17, в эту задачу не входят.

Очередь RAM — до 64 ID (настройка 1..256), один consumer и одна активная запись. Полные тексты не кладутся в очередь/сигналы/шину; payload извлекается после claim. Остальные pending остаются в SQLite, поэтому переполнение пачки не теряет сохранённые уведомления и не требует HTTP-ошибки. Это не ограничение общего числа уведомлений на диске; retention 30 дней продолжает действовать, в том числе для pending. Порядок FIFO по ID, приоритеты уведомлений пока не меняют его. Использовать один процесс/worker Core на SQLite, многопроцессная обработка не поддерживается.

После commit приёма POST только подаёт Event-сигнал и сохраняет прежний receipt stored/duplicate/skipped. Fallback-опрос 1 с находит pending даже без сигнала. Перед чистой асинхронной обработкой короткий UPDATE фиксирует processing/attempts, транзакция не удерживается во время ожидания. Проверяются допуск, TTL и формат; повтор delivery не создаёт новую задачу. Ошибка/таймаут/неверный JSON завершают запись failed с безопасным кодом, следующая продолжает обрабатываться. Автоповтора terminal failed и HTTP-кнопки retry пока нет.

Результат допускается только по строгой схеме ProcessingResult, без отражения входного текста и неизвестных полей. При ошибке финальной записи сохраняется один проверенный результат в RAM и повторяется только его commit, health сообщает storage_error. При неопределённом исходе claim после восстановления БД незавершённое возвращается pending; обработчик ещё не вызывался. Сырые исключения/SQL-параметры/результаты не логируются. После удаления/истечения TTL/снятия приложения с допуска результат не восстанавливает строку. Временное содержание активной попытки может оставаться в RAM до её окончания; немедленное уничтожение RAM/SQLite/WAL/копий не гарантируется.

Остановка ждёт активную попытку до 5 с (0.1..30), затем отменяет её; queued ID остаются durable pending. После аварии/отмены незавершённый processing восстанавливается pending с PROCESSING_INTERRUPTED и прежним счётчиком попыток, потом получает новый номер. Готовые/failed не пересчитываются. Гарантия — повторяемое чистое вычисление с durable-статусом, а не exactly-once; поэтому процессору запрещены прямые команды HA/внешние побочные действия. Таймаут 30 с (0.1..300), контракт async/cancellation. Синхронный CPU-инференс нельзя помещать в event loop: отдельный исполнитель и отмена занятой модели относятся к TASK-16.

GET /notifications и /notifications/{id} возвращают новые processing_* поля. Старый status=stored/processed сохранён, точную диагностику даёт processing_status. Есть фильтр ?processing_status=failed. Health services.notification_worker: starting/disabled/idle/processing/storage_error/stopped; состояние локальной модели сообщается отдельно. [Контракт](../docs/api-spec.md#414-состояния-обработки--task-15), [отчёт](../docs/reports/task-15.md).

## Локальный движок LLM (программная TASK-16)

Движок выключен по умолчанию. `LLM_ENABLED=true` запускает фоновую загрузку заранее подготовленной GGUF; получение уведомления само по себе модель не скачивает и не вызывает. Извлечение и связь с worker относятся к TASK-17, оценка качества — к TASK-18. `ready` в health подтверждает только загрузку движка. Базовый Docker-образ работает без optional-зависимости; для реального инференса нужен отдельный CPU build с requirements-llm.txt и смонтированная локальная модель.

Подготовка на Linux из корня репозитория, **только до автономного запуска**:

```bash
cd core
CMAKE_BUILD_PARALLEL_LEVEL=2 CMAKE_ARGS='-DGGML_CUDA=OFF -DGGML_RPC=OFF' \
  .venv/bin/python -m pip install -r requirements-llm.txt
cd ..
python3 scripts/download_model.py --model tinyllama
python3 scripts/download_model.py --model qwen
```

Загрузчик закрепляет revision/размер/SHA-256 в scripts/models.json, продолжает `.part` только при согласованном HTTP Range, проверяет весь файл и атомарно публикует `.gguf`. Lock не допускает двух записывающих процессов. Повторный запуск проверяет готовый файл. Старый `MODEL=qwen bash scripts/download_model.sh` поддерживается. Модель и частичные файлы игнорируются git; существующая повреждённая модель заменяется лишь после проверки нового файла.

В локальном `.env` включить LLM и выбрать путь. Настройки (изменение требует перезапуска):

| Переменная | По умолчанию | Граница |
| :--- | :--- | :--- |
| LLM_ENABLED | false | Явное включение |
| LLM_MODEL_PATH | ./models/tinyllama-1.1b-chat-v1.0.Q4_K_M.gguf | Локальный GGUF, до 2 GiB |
| LLM_CONTEXT_SIZE | 1024 | 256..2048 токенов, включая ответ |
| LLM_THREADS | 2 | 1..4 CPU-потока, GPU выключен |
| LLM_MAX_TOKENS | 128 | 1..256 выходных токенов |
| LLM_MEMORY_LIMIT_MB | 2304 | 512..2560 MiB RLIMIT_AS дочернего процесса |
| LLM_LOAD_TIMEOUT_SECONDS | 120 | 1..300 секунд |
| LLM_INFERENCE_TIMEOUT_SECONDS | 30 | 0.1..300 секунд |

Один дочерний Python/llama.cpp-процесс принимает ограниченный JSON-протокол по stdio, без публичного HTTP-порта. Загрузка/хеширование/CPU-инференс не выполняются в event loop Core. Сообщения до 32 KiB суммарно, кадр до 64 KiB, один запрос одновременно, второй сразу LLM_BUSY без очереди payload. Контекст модели может оказаться меньше допустимого размера сообщения: тогда LLM_CONTEXT_EXCEEDED. При превышении времени/отмене процесс terminate→kill/reap, память модели освобождается ОС; следующий потребитель должен явно загрузить модель снова. Core останавливает worker до модели, затем HA/БД. Параметры — n_batch=n_ubatch=64, temperature=0, seed=42, mmap=true, mlock=false. Виртуальный лимит RLIMIT_AS включает mmap/библиотеки, **не равен измеренному RSS и не доказывает, что весь стек уложится в 4 GB**.

Окружение дочернего процесса не содержит API/HA-ключей и proxy, Python-аудит запрещает connect/DNS; используются только локальный путь и offline-переменные. Нативные stdout/stderr перенаправлены в /dev/null, исключения наружу идут фиксированными кодами. Тексты не попадают в служебные логи. Это не изоляция недоверенного нативного кода ОС: устанавливать доверенный пакет/модель, для проверки без сети дополнительно использовать контейнер `--network none`. Память/KV-cache не является защищённым хранилищем и не обещает криптографическое стирание.

Воспроизводимые стенды используют только синтетику, одноразовые БД и настройки в core/.pytest_cache, не читают рабочий `.env`:

```bash
cd core
.venv/bin/python checks/check_llm.py --model models/tinyllama-1.1b-chat-v1.0.Q4_K_M.gguf
.venv/bin/python checks/benchmark_llm.py \
  --model models/tinyllama-1.1b-chat-v1.0.Q4_K_M.gguf \
  --model models/qwen2.5-1.5b-instruct-q4_k_m.gguf \
  --context 1024 --context 2048 --threads 2 --threads 4 \

```

Первый стенд проверяет полный lifespan Core, HTTP во время загрузки/инференса, настоящую отмену/повторную загрузку. HA — MockTransport, HTTP — ASGITransport. Второй сохраняет версии/CPU/хеш модели и набора, загрузку, токены, задержки и ru_maxrss процесса для каждого профиля. 8 классификационных примеров — предварительный smoke, не подтверждение целевой точности TASK-18. Результат на компьютере не заменяет Pi/охлаждение/совместный RAM-бюджет.

## Извлечение уведомлений (программная TASK-17)

Включение в локальном `.env` после подготовки проверенного GGUF:

```dotenv
LLM_ENABLED=true
LLM_MODEL_PATH=./models/qwen2.5-1.5b-instruct-q4_k_m.gguf
LLM_CONTEXT_SIZE=2048
LLM_MAX_TOKENS=256
LLM_INFERENCE_TIMEOUT_SECONDS=45
NOTIFICATION_PROCESSOR=llm
NOTIFICATION_PROCESSING_TIMEOUT_SECONDS=60
NOTIFICATION_TIMEZONE=Asia/Yekaterinburg
```

Это явный пример настройки для проб, не принятый профиль Raspberry Pi. Без обоих переключателей реальная обработка не начинается. Worker ждёт готовности модели до claim, показывает waiting_model/model_unavailable, сохраняет pending без расходования attempts. Ошибка загрузки не уничтожает backlog. После timeout/отмены/выхода процесса перед следующим событием делает явную повторную загрузку; persistent load/inference failure требует устранения причины и перезапуска. Готовые и failed не пересчитываются. Прежний diagnostic поддерживается независимо и не становится анализом текста.

Русский промпт с тремя отдельными синтетическими примерами отделяет инструкции от JSON title/text. Вывод ограничен схемой, затем проверяются типы, размеры, enum, дубликаты ключей, отсутствие лишних полей и буквальное наличие извлечённых subject/location/service/time_expression в title/text. Неподтверждённые факты/обрезанный ответ → LLM_BAD_RESPONSE, исходный ответ не сохраняется/не логируется. Валидность цитаты не доказывает смысловую правильность категории или сущности — это измеряет TASK-18. Банки/мессенджеры и календарные источники в allowlist автоматически не добавляются.

Категории версии 1: delivery/transport/calendar/reminder/noise. Распознанный приоритет low/default/high отделён от Android priority. Intent — описательный delivery_event/transport_event/calendar_event/reminder/none; **action_authorized всегда false**, команд/HA-параметров нет. Ни один обработчик не получает HAClient. Success сохраняет category/проверенный processed_data через прежний finish, без новой схемы БД; filter category работает. POST receipt остаётся прежним, результат доступен только через защищённые GET. [Полная схема и правила времени](../docs/api-spec.md#415-результат-извлечения--программная-task-17).

Относительные даты рассчитывает код от timestamp уведомления и NOTIFICATION_TIMEZONE, а не день запуска worker. Поддержаны явные интервалы минут/часов/дней, сегодня/завтра/послезавтра, ISO/дд.мм.гггг с необязательным временем. Без часов — date_only, не выдуманная полночь. Голые часы дополняются днём только при единственной буквальной цитате сегодня/завтра/послезавтра в исходном тексте. Неподдержанный формат/день недели/диапазон/двойной или пропущенный час DST — unresolved с буквальным источником, без назначения действия. Перед использованием в будущем расписании проверять resolution/срок/подтверждение отдельно.

Полный синтетический стенд с настоящей моделью:

```bash
cd core
.venv/bin/python checks/check_extraction.py \
  --model models/qwen2.5-1.5b-instruct-q4_k_m.gguf \
  --output ../docs/reports/task-17-samples.json
```

Он временно допускает только синтетические приложения Ozon/Calendar/Keep в одноразовом каталоге; рабочий `.env` и его политику не меняет. Проверяет получение receipt без ожидания inference, четыре результата/нормализацию, сохранение после нового lifespan, duplicate без нового inference и отсутствие команд HA. HTTP — ASGITransport, HA — MockTransport; это не телефон/Pi. Код возврата 1 при неверной категории/времени, отчёт сохраняет ошибки. Примеры служат отладке, не независимому подтверждению целевого качества.

Полный pytest на Python 3.11 можно воспроизвести в отдельном **тестовом**, не рабочем образе. Из core/ (при сборке нужен доступ к пакетам, сам pytest без сети):

Последний отдельный стенд запускает синтетический HTTP HA и дочерний Core на loopback со случайными ключами/портом и временной БД .pytest_cache/task15-loopback-*. Пока обработчик ожидает, проверяет HTTP, команду HA, 12 ожидающих записей и duplicate. Затем SIGKILL и новый процесс Core с той же БД: processing восстанавливается с новой попыткой, готовая запись повторно не вычисляется. Также проверяет failed/invalid/timeout/продолжение, integrity_check, отсутствие синтетического текста исключения и ключей в БД/логах/stdout. Только тестовый --serve использует управляемые отказы, runtime diagnostic их не содержит. Временный каталог/процессы очищаются. Рабочие .env/HA/БД не используются; это не проверка Pi или модели.

## Профиль присутствия (программная TASK-20)

Аналитика выключена по умолчанию. Для синтетики/осознанной настройки:

```dotenv
HA_TELEMETRY_ENTITIES=["binary_sensor.home_presence"]
ANALYTICS_PRESENCE_ENTITY=binary_sensor.home_presence
ANALYTICS_TIMEZONE=Asia/Yekaterinburg
ANALYTICS_INTERVAL_SECONDS=3600
```

Требуется именно сигнал присутствия on=дома/off=вне дома; обычный датчик движения не подходит автоматически. Аналитика не добавляет сущность в сбор и не выполняет команды. Изменение .env требует перезапуска; выключение удаляет производные профили/снимок, исходную телеметрию не трогает. Штатные правила миграции/резервной копии сохраняются, новый head — 0007_habit_profiles.

GET /api/v1/habits с Bearer возвращает описательные профили/окна, число наблюдений и причины исключений, stale/telemetry_stale. Default habits=[]/disabled. Исторический ready не означает актуальное присутствие, пригодность сценария или разрешение действовать. Подробные пороги/формула confidence — [контракт](../docs/api-spec.md#43-аналитика--программная-task-20); score эвристический, не вероятность.

30 полных локальных дней, отдельно будни/выходные, первый уход/последний приход. Gaps/snapshot/unknown/неверные часы/дребезг не превращаются в события. Чтение до 10000 наблюдений/1000 gaps, CPU вне event loop; до 4 профилей/один снимок, периодический пересчёт с атомарной заменой. Предложения/исполнение пока отдельные задачи.

Проверки: `pytest -q tests/test_analytics_engine.py tests/test_analytics_service.py tests/test_migrations.py`; отдельный `checks/check_analytics.py --output <новый.json>` проверяет настоящий loopback HTTP и перезапуск без HA/LLM на временной синтетике. Рабочие .env/данные не используются. [Результаты и ограничения](../docs/reports/task-20.md): 297 Core/Python 3.14 и 3.11 network none, реальные 7–10 дней/Pi ещё не подтверждены.

## Предложения и локальные подсказки (программная TASK-21)

По умолчанию управляемых целей нет: `AUTOMATION_ALLOWED_LIGHTS=[]`. Разрешать только конкретные light.*, до20; `SUGGESTIONS_INTERVAL_SECONDS=30` (5..3600). Нужен выбранный датчик и свежие профили TASK-20 со score≥0.75. Принять предложение можно только с явной целью; отклонение/отключение сохраняются, изменение условий/политики требует подтверждения заново. Исполнителя пока нет: enabled — действующее согласие, executable=false. Настройки рабочего .env автоматически не меняются.

GET `/api/v1/automations`, деталь/20последних решений, POST `/automations/refresh` и `/{id}/decision` защищены Bearer. Решение содержит decision/version и target_entity только для accept.409 требует перечитать условия, повторять POST автоматически нельзя. Контракт — [API](../docs/api-spec.md), ограничения — [отчёт](../docs/reports/task-21.md).

GET `/api/v1/hints?after_id=0&limit=20`: постоянный feed_id, latest_id, next_id и общие подсказки без личного текста. Каждый клиент хранит свой cursor. При новом feed_id/сбросе ID клиент начинает с последнего события, не уведомляет о старом. TTL7дней/1000строк. Создание требует свежего live прихода без gap и валидной канонической обработки delivery; одноразовый переход/cooldown1час/контекст раз в сутки. Это подсказка, не команда и не доказательство доставки телефона.

Короткие пишущие транзакции telemetry/analytics/suggestions резервируют SQLite writer до чтения (`sqlite_immediate`), чтобы избежать WAL BUSY_SNAPSHOT; сеть и вычисления остаются вне транзакций. Один процесс Core на БД.

Из core/: `.venv/bin/python checks/check_suggestions.py --help` — синтетический HTTP/HA WebSocket/перезапуск, собственная временная SQLite, без GGUF/рабочего HA. Результат сохранён в docs/reports/task-21-loopback.json. Обычные pytest по-прежнему не открывают TCP.
