# Shade Web — дашборд Shade AI

Локальный React + Vite + TypeScript интерфейс: диагностика Core/HA, история уведомлений с просмотром записи, журнал попыток команд HA. [Контракт API](../docs/api-spec.md), [результаты TASK-07](../docs/reports/task-07.md).

## Запуск

```bash
cd web
npm ci
npm run dev        # http://localhost:5173; /api → localhost:8000
```

Core запустить по [инструкции](../core/README.md). В dev-режиме Vite проксирует API, в production раздачу web/dist и прокси нужно настроить отдельно в TASK-08. FastAPI пока не раздаёт статические файлы веба.

## Подключение и работа

1. Откройте «Подключение к Core», введите SHADE_API_KEY из локального файла настроек Core и нажмите «Сохранить ключ». Health работает без ключа; 401 в истории не скрывает состояние сервера.
2. Ключ хранится только в localStorage этого браузера, без шифрования. На общем компьютере используйте «Удалить ключ» после работы: история и открытая запись сразу скрываются. Если браузер запрещает storage, ключ действует в памяти страницы и показывается сообщение об этом. Уже сохранённый ключ при запрете удаления может остаться в storage — интерфейс сообщает об отказе.
3. «Уведомления»: по 20 записей на страницу; нажмите на запись для полного текста, времени получения/события и состояния обработки. Enter открывает запись, Escape закрывает и возвращает фокус. Tab/Shift+Tab остаются в окне.
4. «Журнал команд»: по 20 попыток на страницу, фильтр результата. «Принята HA» означает принятие сервиса, а не проверенное физическое действие. При unknown команда могла выполниться; автоматического повтора нет. Управления устройствами на этом экране пока нет.

У каждого раздела свои загрузка/ошибка/пустой список/обновление. При временном отказе последние данные остаются с подписью времени, при 401 скрываются. Смена ключа очищает прежние списки и окно записи. Запросы отменяются при смене страницы/фильтра/ключа; запоздавший ответ не заменяет новую страницу. После удаления старых записей offset корректируется к существующей странице.

Опрос — примерно каждые 10 секунд после завершения предыдущего запроса, без перекрывающихся циклов. В скрытой вкладке периодические запросы приостанавливаются; возврат во вкладку и событие online запускают обновление. Время ожидания запроса ограничено 12 секундами. Время записей показано в часовом поясе браузера. Списки не сохраняются в localStorage, fetch использует no-store. При offset-пагинации новая запись между запросами может сдвинуть страницу — это ограничение текущего API.

Health различает ok/degraded/error, доступность БД/HA и состояние локального движка LLM: не загружен, загрузка, готов, недоступен. Готовый движок не означает подключённые извлечение/привычки. Неизвестный код ошибки модели не отражается raw. Структурированный HTTP 503 от /health показывается как диагностика отказа БД. Отсутствие HA не мешает просматривать сохранённую историю. Таймер health независим от ошибок защищённых запросов.

Палитра и слои — из [брендбука](../docs/brand.md), без внешних шрифтов, иконок, аналитики и CDN. Если Inter/JetBrains Mono не установлены локально, используются системные fallback-шрифты. Анимация учитывает prefers-reduced-motion. Проверены Chromium и ширины 1440/390/320 px; другие браузеры/скринридер/физический телефон отдельно не проверялись.

## Воспроизведение браузерной проверки

Для приёмки есть отдельный [Core-стенд](checks/server.py). Он создаёт временную БД/логи в core/.pytest_cache, подставляет синтетические настройки до импорта Core и использует HA MockTransport. Рабочие .env/БД/HA не читаются. Все 45 уведомлений и 24 попытки команд создаются через настоящий API Core. Стенд доступен только на 127.0.0.1:8000; остановите свой dev-Core, если этот порт занят. Синтетический ключ указан в исходнике стенда и не подходит для рабочего Core.

Из корня проекта, в двух терминалах:

```bash
core/.venv/bin/python web/checks/server.py
```

```bash
cd web
npm run dev -- --host 127.0.0.1 --strictPort
```

Нужны Playwright CLI и установленный браузер. Из web/ с отдельным тестовым профилем:

```bash
npx --yes --package @playwright/cli playwright-cli -s=shade-task07 open http://127.0.0.1:5173
npx --yes --package @playwright/cli playwright-cli -s=shade-task07 run-code --filename checks/browser.js
npx --yes --package @playwright/cli playwright-cli -s=shade-task07 run-code --filename checks/edge-cases.js
npx --yes --package @playwright/cli playwright-cli -s=shade-task07 close
```

При нестандартном пути браузера передайте open --config с локальным конфигом CLI; конфиг и профиль не коммитить. checks/browser.js пишет снимки в output/playwright/ (каталог должен существовать: `mkdir -p output/playwright`). Эта папка и .playwright-cli/ игнорируются git. Сценарии завершаются ошибкой при провале проверки; дополнительные 404/пустой список/503/задержки имитируются browser routes, offline — сетевым режимом браузера. Основные списки/авторизация/журнал читаются из настоящего тестового Core. После проверки остановите оба сервера через Ctrl+C; временная БД удаляется при штатной остановке. Не запускайте pytest одновременно со стендом: pytest очищает свой временный каталог.


## Сопоставление с Android (программная TASK-13)

В деталях уведомления показан UUID отправителя под подписью «Идентификатор события». Его можно сопоставить с UUID в локальном Android-журнале; серверный ID и локальный ID Android могут различаться. Для legacy без event_id отображается «Старая запись без UUID». Контракт Core не менялся.

[Сквозной сценарий](checks/android-journal.js) запускается через [Android helper](../android/checks/check_journal_web.py) после checks/check_journal.py со свежим отдельным Core. Он использует метаданные синтетической записи из android/.gradle/task13-checks/event.json, проверяет текст/UUID/время, две записи без дублей, 320 px/Escape/reload и отсутствие внешних запросов/JS-ошибок. Нужны существующий Playwright CLI wrapper и локальный Vite; новые зависимости проекта не требуются. [Порядок запуска](../android/README.md#воспроизведение-программной-task-13), [отчёт](../docs/reports/task-13.md).


## Статусы обработки Core (TASK-15)

История и карточка учитывают processing_status: ожидание, обработка, ошибка, результат. Карточка показывает число попыток и безопасную причину; неизвестный код заменяется общей подписью. Диагностический результат помечен «Проверка очереди завершена», с явным пояснением об отсутствии анализа текста/LLM. Старый Core без processing_* поддерживается прежним status. Карточка опрашивается каждые 5 секунд, списки — каждые 10; скрытая вкладка не опрашивается, закрытие/смена ключа отменяют запросы через общий useResource.

Новый CLI-сценарий [processing.js](checks/processing.js) запускается с тем же изолированным Core/Vite/Playwright, что проверка TASK-07:

```bash
npx --yes --package @playwright/cli playwright-cli -s=shade-task15 open http://127.0.0.1:5173
npx --yes --package @playwright/cli playwright-cli -s=shade-task15 snapshot
npx --yes --package @playwright/cli playwright-cli -s=shade-task15 run-code --filename checks/processing.js
npx --yes --package @playwright/cli playwright-cli -s=shade-task15 close
```

Список берётся из реального тестового Core, переходы processing/failed/diagnostic в ответе одной карточки имитируются browser route. Проверяются обновление уже открытой карточки, fallback неизвестной ошибки без raw-кода, 320 px и отсутствие внешних запросов/JS-ошибок. Настоящую очередь и SIGKILL/рестарт проверяет отдельный Core-стенд, эти проверки различать. Снимок — игнорируемый output/playwright/task15-processing.png. Сначала создайте `mkdir -p output/playwright`; профиль/локальный config не коммитить.
